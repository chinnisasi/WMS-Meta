- **Stock adjustments bypass the secure-bin authority gate too** *(12-3)* — `stock.adjust` is capability-gated (`stock.adjust`: owner/ops_manager) but class-blind, so non-secure-role stock seeding into a secure bin happens through the named bypass (every 12-1/12-2/12-3 e2e fixture does exactly this). - **Stock adjustments bypass the bulk-asset occupancy gate too** *(12-4)* — `bulkAssetOccupancyHolds` runs in the placement/merge/suggestion arms; `stock.adjust` is type-blind, so a second SKU can be parked in a holding tank by an adjustment — the same pre-existing currency as the four gaps above, now on the 12-4 gate. - **The bulk re-value guard counts on-hand load only** *(12-4 review 2)* — `qc_holds` carries no quantity, so held mass attributed to an origin bin is not computable from the hold rows; a release returning held units into a bulk asset re-valued below (on-hand + held) mass would over-fill it. - **A concurrent adjustment races a placement past a stale load** — the bin-row `.for('update')` serializes only gate-compliant writers; adjust takes no bin-row lock (pre-existing for the unit gate; 11-5 widens the currency, not the mechanism) *(11-5 review, deferred-work)*

Recorded as accepted currency beside the adjustment bypass, not as a defect. *(12-2)* The 12-2 placement gate widens the currency: the placement SKU read now carries `hazardClass` too, unlocked by the same shape — a hazard edit could commit inside the same window (and the hazard-edit guard locks only the SKU row, like the class edit)
- **The suggestion walk, task derivation and wave pool are role-blind** *(12-3, decided 2026-09-24)* — a secure bin can be *suggested* to an operator, whose command then 403s `role-denied` naming `secure.move` with nothing written: advisory suggestion, binding gate. ## invoicing

*(8-1 built the GST invoice core; entries below are its known-not-done.)*

- **No `invoice.void`, no credit notes** — the `status` CHECK carries `voided` for vocabulary stability, but no command reaches it. A mis-priced issued invoice can be re-derived (revision bumps, number kept) but not cancelled *(8-1 Never-rule)*
- **GSTINs are stamped at create only** — `tenants.gstin` at registration, `warehouses.gstin` at warehouse create, `orders.consignee_gstin` at order create. No route edits any of them afterwards (tenancy's only PATCH is the bin edit); a tenant that registered without a GSTIN can only gain one by a future settings route *(8-1 triage #3)*
- **An issued invoice is re-derived IN PLACE under the same number.** A regenerate after a catalog change (name, HSN, `gst_rate_bps`) rewrites an issued invoice's money and lines and bumps `revision`, keeping `invoice_no`. The spec's I/O matrix sanctions this ("changes → revision bumps"), and only the first issuance emits `invoice.issued`, so a revision's new totals reach no consumer. Whether an issued tax document may change at all, or must change through a credit/debit note, is 8-2's regulatory call *(8-1 code review, rejected as spec-sanctioned)*
- **Numbering is per tenant per FY, not per GSTIN.** `invoice_series` is unique on `(tenant_id, fy_label)`, but a tenant can invoice under several GSTINs (one per warehouse state), so each GSTIN's own sequence has gaps. Rule 46 asks for a consecutive series per registration. The Design Notes pinned per-tenant; 8-2 should rule on it *(8-1 code review, rejected as spec-sanctioned)*
- **`document.totals.payAble` has odd casing**, pinned verbatim in the Design Notes. Rename it (a document-shape change, with a revision bump on re-derive) before 21-5 or more FE code freezes it *(8-1 code review)*
- **Payable is paise-exact; GST practice rounds the payable to a rupee** — stored math deliberately does no rupee rounding. Whether the printed/filed figure rounds, and where, belongs to 8-2's regulatory pass *(8-1 triage #5)*
- **No backfill** — orders dispatched before 8-1 shipped have no invoice until someone calls `POST /invoices` for them; no event replay, no bulk job *(8-1 Never-rule)*
- **`invoice.issued` has no consumer** — appended in-tx by both the delivery handler and the command; 8-2 (e-way/HSN) and 21-5 (3PL billing) are the intended readers. An `awaiting-data → issued` flip is therefore invisible to an open `/compliance` page until reload *(8-1 triage #11)*
- **A data-faulted dispatch leaves no invoice, and nothing lists it** — the `order.dispatched` delivery ACKs deterministic failures (unknown/undispatched order, arithmetic overflow) so the 7-2 channel writeback sharing the event is never starved; the fault is an error log only. No surface lists dispatched-but-uninvoiced orders, so recovery (`POST /invoices`) depends on someone reading the log. The bus-level fix — per-subscriber isolation in `RoutedEventBus` — is the spine change 8-1 declined *(8-1 code review D3)*
- **Kit orders always park `awaiting-data`, even when priced at create**. The parent's `ratePaise` drops with the zero-pick parent line, and components are exploded with `rate_paise = null`, so every kit dispatch needs per-component manual pricing through `POST /invoices`. Splitting the parent's rate across components needs a remainder rule designed on purpose *(8-1 code review, deferred by decision)*
- **Channel-ingested orders always park `awaiting-data`** — marketplace payloads carry prices the 7-2 ingest does not map to `ratePaise`, so every channel order needs a manual pricing pass. Mapping the channel's line price at ingest is the obvious fix; it needs a decision on tax-inclusive vs exclusive marketplace prices *(8-1)*

## How to use this

1. **Before speccing a story**, read your module's section. A listed item with the fix already diagnosed is usually cheaper to fold in than to schedule separately.
2. **When a review defers something**, it lands in `deferred-work.md`, which is the authority. This file is a **hand-written digest** of it — no generator exists. When the two disagree, `deferred-work.md` wins; fix this file rather than the other way round.
3. **Epic retrospectives** are where open action items get claimed into a story or explicitly closed. *"Every open retro item claimed into a story spec or explicitly closed at the next epic boundary"* is itself an open process commitment *(epic-3 retro a11)*.
