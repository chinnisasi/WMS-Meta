- **Stock adjustments bypass the secure-bin authority gate too** *(12-3)* — `stock.adjust` is capability-gated (`stock.adjust`: owner/ops_manager) but class-blind, so non-secure-role stock seeding into a secure bin happens through the named bypass (every 12-1/12-2/12-3 e2e fixture does exactly this). - **Stock adjustments bypass the bulk-asset occupancy gate too** *(12-4)* — `bulkAssetOccupancyHolds` runs in the placement/merge/suggestion arms; `stock.adjust` is type-blind, so a second SKU can be parked in a holding tank by an adjustment — the same pre-existing currency as the four gaps above, now on the 12-4 gate. - **The bulk re-value guard counts on-hand load only** *(12-4 review 2)* — `qc_holds` carries no quantity, so held mass attributed to an origin bin is not computable from the hold rows; a release returning held units into a bulk asset re-valued below (on-hand + held) mass would over-fill it. - **A concurrent adjustment races a placement past a stale load** — the bin-row `.for('update')` serializes only gate-compliant writers; adjust takes no bin-row lock (pre-existing for the unit gate; 11-5 widens the currency, not the mechanism) *(11-5 review, deferred-work)*
- **The class gates read the SKU unlocked** *(12-1 deferred)* — the placement, pick draw and wave/allocation pool read the SKU's `storageClass` unlocked, and the SKU class edit locks only the SKU row, so a class edit can commit between a placement/pick's SKU read and its bin write. Recorded as accepted currency beside the adjustment bypass, not as a defect. *(12-2)* The 12-2 placement gate widens the currency: the placement SKU read now carries `hazardClass` too, unlocked by the same shape — a hazard edit could commit inside the same window (and the hazard-edit guard locks only the SKU row, like the class edit)
- **The suggestion walk, task derivation and wave pool are role-blind** *(12-3, decided 2026-09-24)* — a secure bin can be *suggested* to an operator, whose command then 403s `role-denied` naming `secure.move` with nothing written: advisory suggestion, binding gate. Since 8-1d the invoice's `pos-discrepancy` warning says so at issue ("dispatch-from discrepancy … if an e-way bill is required it will be blocked (ship-to-differs); generate it on the portal"), and the web warehouse form warns inline when a typed GSTIN's state differs from the origin state. Still not prevented: GSTINs cannot be added after creation, so the only fix is a new warehouse *(epic-8 retro S4)*
- **No live e-way adapter** *(8-2b Decision 1, OQ3)* — production runs `unconfiguredEwayGateway`; bills go through the NIC bulk JSON and a recorded number. A live GSP/NIC adapter needs: sealed per-GSTIN credentials (the AD-15 vault pattern — never env), metering through the adapter port (AD-17), the bulk→API key renames (`transType`→`transactionType`, `actualFromStateCode`→`actFromStateCode`, `OthValue`→`otherValue`, `TotNonAdvolVal`→`cessNonAdvolValue`), auth/encryption, and the port contract's look-up-before-generate by (GSTIN, `INV`, docNo)
- **No e-invoicing / IRN** — a GSTIN flagged "e-invoicing applies" holds its B2B bills as `needs-irn` forever (NIC refuses them without an IRN since 1 Mar 2024); the only exit is generating on the portal after an IRN is obtained elsewhere, then recording the number
- **No Part B update after generation, and the 15-day Part-A-only lapse is not tracked** — a bill generated with a transporter ID only (no vehicle) lapses unless Part B is added on the portal within 15 days; nothing here reminds anyone (the screen states it)
- **No extension or cancellation** of a generated EWB (validity extension, 24-hour cancellation) — a recorded number is final
- **`transType` 2–4 never exported** *(Decision 8)* — bill-to ≠ ship-to (`ship-to-differs`, the `pos-discrepancy` case) is blocked terminally; finance generates it on the portal by hand
- **Exports, SEZ and Other Territory (97/99)** — `unsupported-supply` blocks POS 97/99; an SEZ consignee is **undetectable** (nothing marks an SEZ GSTIN) and exports as a domestic B2B bill. Since 8-1d a consignee GSTIN prefix of 99 no longer resolves the place of supply (it is refused at entry; a legacy one falls back to the address text and warns `gstin-prefix-unknown`), so POS 99 now arises only from an address reading "Other Country" (see the seed-label row above)
- **No grouping above 250 lines** — `too-many-lines` is terminal; NIC's 250-item cap would need HSN-wise grouping, deliberately not done
- **Zero-rated exports are counted as exempt** — the consignment value excludes every 0% line (Rule 138 Explanation 2), which is right for exempt goods and wrong for zero-rated supplies (not modelled: no export flag)
- **Document numbers starting with `0` are unverified at NIC** — invoice numbers start with the GSTIN state code (`07/2627/000001` for Delhi); whether NIC's bulk validator accepts a leading zero in `docNo` has not been checked against the portal
- **The NIC rate allow-list goes stale** — `NIC_RATE_BPS` is the 1.0.0621 workbook's table plus 4000 (GST 2.0, 22 Sep 2025); a rate NIC adds later reads as `rate-not-standard` until the code list moves. It should become versioned reference data like the thresholds
- **A data-faulted `invoice.issued` leaves no bill, and nothing lists it** — the e-way delivery ACKs deterministic failures (no threshold in force, an arithmetic overflow, an unresolved supply type) with an error log line only, so that consignment gets no e-way bill and appears on no screen (the mirror of the invoicing entry above). Recovery today means reading the log
- **Services-only (SAC, chapter 99) lines are treated as goods** — they count toward the consignment value and are emitted as items; NIC needs at least one goods HSN on a bill, and a services-only invoice should need no bill at all. Nothing distinguishes SAC from HSN yet
- **Threshold changes never re-evaluate** — an override is read only when an `invoice.issued` is delivered, so it affects invoices issued after it is added (whose IST date is on or after its `effective_from`); bills already queued, and invoices that were not queued, are never revisited (stated on the screen). No backfill of invoices issued before 8-2b deployed

## How to use this

1. **Before speccing a story**, read your module's section. A listed item with the fix already diagnosed is usually cheaper to fold in than to schedule separately.
2. **When a review defers something**, it lands in `deferred-work.md`, which is the authority. This file is a **hand-written digest** of it — no generator exists. When the two disagree, `deferred-work.md` wins; fix this file rather than the other way round.
3. **Epic retrospectives** are where open action items get claimed into a story or explicitly closed. *"Every open retro item claimed into a story spec or explicitly closed at the next epic boundary"* is itself an open process commitment *(epic-3 retro a11)*.
