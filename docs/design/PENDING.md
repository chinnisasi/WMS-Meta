## inventory

- **Reservation rebuild single-flight is per process (cross-instance limit)** — the `inFlight` map in `ReservationService` deduplicates rebuilds of one warehouse within a process only. Two instances can still rebuild the same warehouse at once (as the not-ready grant repair always could), and an overlap's forced counter SET can drop an increment a grant made between them — the counter reads LOW until the next parity pass heals it. If multi-instance deploys arrive, a Valkey-side lock (or a fenced rebuild epoch) belongs here *(cold-warehouse fix, design review #5/#6)*
- **A cold warehouse's first read pays a rebuild inline** — the ATP read that finds a warehouse not-ready runs one journal rebuild (two journal-sum reads and one counter SET per SKU) before answering, on order intake's request path too. There is no deadline race, and concurrent reads join one flight. After a Valkey flush every warehouse is cold at once, so the first wave of reads across warehouses is a herd of per-warehouse rebuilds (one each, not one per read). Revisit with a measured latency budget or an eager post-flush rebuild if it shows up *(cold-warehouse fix, design review #5)*
- **Grant ceiling vs concurrent adjustment race** — the module header claims "never oversells"; the actual guarantee is narrower. Either re-validate committed on-hand after the Valkey win, or weaken the claim *(epic-2 retro a2)*
- **Reconciliation starvation** — never-checkpointed partitions are not re-queued on failure, and no periodic full pass exists, so the bounded-scan escape hatch is unreachable *(epic-2 retro a6)*
- **Verification gaps**: `exportDigest`'s three refusal arms, ~~`anchorChain`'s empty-ledger arm~~ (**9-3c:** now the typed no-op `{nothing: true}`, pinned by `test/ledger-integrity.spec.ts` "an empty warehouse" and `test/ledger.spec.ts`'s nothing-new arm) and concurrent-anchor case, outbox ack-delete failure injection, the reconcile failure stamp, `parseLastDivergences` malformed entries *(epic-2 retro a7)*
- **No withdraw/cancel verb or TTL for abandoned adjustment pends** — a pend raised in error lives until an owner rejects it; the frozen 5-2 intent settles the flow as pending→decide with exactly two outcomes *(5-2 review, deferred-work)*
- **A pend whose FEFO-resolved batch is consumed before approval always 422s** — reject-and-re-raise is the only recourse; re-request/re-resolve belongs to the 5-4/5-5 consolidated review-queue UX *(5-2 review, deferred-work)*
- **The approval-threshold flow cannot be disabled via the API** — PUT requires a non-null threshold and no DELETE/nulling verb exists, so disable is SQL-only; the absent row is the disable mechanism *(5-2 review, deferred-work)*
- **Approve/reject carries no decision note, and the requester is never notified of the outcome** — the decide command records status/decider stamps only, and the outbox notifies the owner at pend creation but nothing answers the requester; both are 5-4/5-5 queue-UX wants *(5-2 review, deferred-work)*
- **`fullPrecisionInstant` discards non-UTC offsets** — it matches and then drops any non-UTC offset in the raw instant, emitting Z; harmless while deployments run UTC session TZ (none pin it in config), a cursor-ordering hazard if one ever doesn't *(5-2 review, deferred-work)*
- **Blocked batch status is unenforced on the draw side** — the FEFO draw does not consult batch status *(epic-2 retro a13)*
- **Typed-error hardening**: `ttlSeconds: 0` should be a 400; ~~`verifyChain` range input is unvalidated~~ (**closed by 9-3c:** non-integers, `fromSeq < 1` or `toSeq < fromSeq` → 400 `validation-failed`, no break row — `test/ledger-integrity.spec.ts`); the int4 ceiling overflow should be a typed 422 *(epic-2 retro a14)*
- **Shared test bootstrap + lock-key registry** — the nine-suite deployment-parity block wants extracting; advisory keys want one registry *(epic-2 retro a10)*
- ~~**Pre-migration ledger hashes no longer verify** — … Nothing schedules `verifyChain` today~~ *(story 10.1)* **Closed by 9-3c (human decision 1, 2026-10-14):** a pre-0026 event is verified in its pre-0026 form (`quantity_delta / 1000` hashed) at or below the warehouse's baseline B, set once by the `LedgerIntegrityWorker` (which also schedules verification: anchoring and the re-verify rotation). An un-baselined warehouse still reads its pre-0026 events as broken (`test/fractional-quantity.spec.ts` keeps that pin and adds the real-0026 proof of the old form)
- **The first baseline holds the warehouse lock over the whole legacy prefix** *(9-3c code review #21)* — `ensureBaseline` scans the pre-0026 prefix with no per-tick cap and commits every `legacy` anchor over `[1..B]` in one transaction under `warehouseAdvisoryLock`, so a warehouse with a large pre-0026 history blocks its ledger appends for the whole first run. Accepted because only dev databases carry pre-0026 events (no production database predates 0026; a fresh one baselines at B = 0). The fix, if it ever matters: commit each legacy chunk in its own lock-scoped transaction and write the state row last
- **No recovery path after a chain break** *(9-3c design, Never list)* — a broken warehouse's tail stops anchoring (verify-before-anchor refuses at the same seq every tick, a WARN re-detection) and `broken_at_seq` is never cleared; acknowledging repairs nothing. There is no re-baseline, no "accept this event" and no way to anchor past the break. Investigating and repairing one is a manual, out-of-band act today; a deliberate, audited recovery command (re-anchor from a named seq, recording who accepted what) is its own design
- **S3 WORM is not provisioned** *(9-3c human decision 2)* — `LEDGER_ANCHOR_WORM` defaults to `none`; dev and CI never touch S3, and the adapter is proven only against a mocked SDK (`test/ledger-anchor-worm.spec.ts`). Going live needs a bucket in ap-south-1 **created with Object Lock**, an IAM role with `s3:PutObject`, `s3:PutObjectRetention`, `s3:GetObject`, `s3:GetObjectVersion` on `ledger-anchors/*` plus `s3:ListBucket` on the bucket, and `LEDGER_ANCHOR_WORM=s3` + `LEDGER_ANCHOR_S3_BUCKET` (the wms-be README). A bucket without Object Lock is discovered only at the first put (logged with its code, retried every tick, the anchors counted as waiting). Run one real put + read-back against the provisioned bucket before relying on it
- **Orphaned S3 versions from a copy race** *(9-3c design review #6)* — two instances copying the same anchor both put; the first committed copy row wins (`ON CONFLICT (anchor_id) DO NOTHING`) and the other object version stays in the bucket, locked and unreferenced. Harmless (the recorded version is the one read back) and bounded by the race; a sweep would need the bucket's version listing
- ~~**A WORM read-back transport error holds the rotation on that anchor**~~ **Closed in the 9-3c code review:** the cursor now advances once the chain re-verify ran; the read-back retries when the rotation comes back round. *(9-3c build)* — the spec retries a network error or 5xx "next tick", so the re-verify cursor does not advance past an anchor whose read-back failed. A persistent S3 outage therefore re-verifies the same anchored range every tick (the chain recompute still runs on it) until S3 answers. Advancing the chain cursor separately from a WORM read-back cursor would decouple them
- **The ledger integrity read is unpaged** *(9-3c design)* — `GET …/inventory/ledger/integrity` returns every warehouse (at most 10 breaks each), bounded only by the warehouse count — a named exception in API-SURFACE. A tenant with hundreds of warehouses wants paging or a warehouse filter
- **The re-verify rotation reads one anchored range per warehouse per tick** *(9-3c design)* — with hourly ticks and ranges of 10,000 events, a warehouse with N anchors is fully re-proved every N hours. A large history wants a time budget per tick instead of a fixed one-range step
- **No ledger link for a QC hold, a bin merge, an excursion or an auto-applied adjustment** *(9-3a design review #22)* — 9-3a links five documents to their events (GRN, PO, order, an approved adjustment, an adjusted variance). A QC hold's events carry `holdId`, a merge's `mergeId`, an excursion's `excursionId`, and an immediate (under-threshold) adjustment names no document at all, but no surface filters on those keys and no 0069 index serves them. Each needs a filter key, a partial index (built per the reporting runbook) and a link
- **Documents decided before 9-3a have no ledger link** *(9-3a design, no backfill)* — `stock_adjustment_pendings.ledger_event_id` and `count_variances.ledger_event_id` are written going forward only, and older approved events carry no `adjustmentPendingId`/`countVarianceId` in their referenceDoc (which cannot be edited — the ledger is append-only). Such rows read `ledgerLinked: false` and show no link; their events are still in the ledger, found by SKU, bin and time
- **The stock list's `order=location` sorts the whole warehouse on every page** *(inventory-screen, decided)* — `listStock` joins `bins` and orders by `(bins.system_owned, bins.code COLLATE "C", sku_id, id)`; no index serves that order (the code lives on `bins`, the keyset spans two tables), so each 200-row page sorts the warehouse's `stock_on_hand` rows. Accepted at today's sizes (the join is warehouse-scoped, plus RLS). If it shows up: a denormalised bin code on `stock_on_hand` with an index, or a materialised location order
- **`COLLATE "C"` is unproven on the dev/CI database** *(inventory-screen build)* — the spec's premise that `en_US.utf8` orders `-` differently holds on glibc but not on the Alpine (musl) Postgres image dev and CI run, where `en_US.utf8` is byte order. The collation test in `test/inventory-surfaces.spec.ts` therefore passes with or without the `COLLATE "C"`; it pins the lexical order, not that the clause is present. A glibc-collated database (production's, if it is one) is where the clause matters
- **No serial lookup by serial number** *(inventory-screen, Never list)* — `GET /tenants/{t}/inventory/serials/{serialId}` takes the internal serial id, never the number printed on the unit, so no search box can use it. A by-number read (`serials.serial_number` is unique per tenant + SKU) would need the SKU as well, or answer every match
- **The ledger-filter EXPLAIN test checks a hand-written query** *(9-3a code review BE9)* — `test/putaway.spec.ts` ("the grnId filter is served by its 0069 partial index") runs `EXPLAIN` on SQL it writes itself, with the `?` predicate in place, under `enable_seqscan = off`. - **Deploying 21-9 surfaces previously stranded putaway work** — approved over-receipt excess on ANY document used to stay in Receiving with no task; after 21-9 it counts as work. Count it before deploy (per warehouse):
  ```sql
  select g.warehouse_id, count(*) as lines
  from goods_receipt_lines l
  join goods_receipt_notes g on g.id = l.grn_id and g.tenant_id = l.tenant_id
  join (select grn_line_id, sum(excess_qty) as excess from over_receipts where status = 'approved' group by grn_line_id) ax on ax.grn_line_id = l.id
  join bins rb on rb.tenant_id = g.tenant_id and rb.warehouse_id = g.warehouse_id and rb.code = 'RECEIVING' and rb.system_owned
  where coalesce(case when l.batch_id is null
          then (select sum(quantity) from stock_on_hand s where s.tenant_id = g.tenant_id and s.bin_id = rb.id and s.sku_id = l.sku_id)
          else (select sum(quantity) from batch_on_hand b where b.tenant_id = g.tenant_id and b.bin_id = rb.id and b.sku_id = l.sku_id and b.batch_id = l.batch_id) end, 0) > 0
  group by g.warehouse_id;
  ```

### licence enforcement (1-6d)

*(1-6d added the per-tenant switch, the receipt's licence phase with its waivable review row, and the order refusal; these are its known-not-done.)*

- **Licences are read without a lock** — a receipt or an order reads the licences committed when it reads them (the 1-2b receiving-policy stance); a withdraw or an edit racing a receipt or an order is not serialised against it, so one of them can be judged against the licence a moment before it changed *(spec decision 8)*
- **The receipt date is the device's clock** — a receipt is judged on `istDateOf(occurredAt)` (the 1-2b shelf-life precedent), so a late replay of a scan made while the licence was valid books, and a device whose clock runs fast or slow is judged on the wrong day. Nothing bounds `occurredAt` against server time *(design review D7)*
- **No scan-time warning on the handheld** — the device snapshot carries no licence facts, so the operator learns of a refusal only from the settled `grn.submit` note ("in licence review"); a scan-time warning needs the coverage in the snapshot *(spec decision 6)*
- **Dispatch, transfers, ASNs, POs and returns are not enforced** — only receipt lines and order create are; an accepted order dispatches whatever the licences read later, a transfer can move drug or food goods into an unlicensed site, and an ASN or PO for uncovered goods is accepted (the gaps read shows it) *(spec "Never")*
- **Refused channel ingests are not listed for operators** — an uncovered channel order answers a typed 422 `licence-not-covered`, metered `validation-failed` and deliberately not retried (the merchant resends once the licence is fixed), but no operator surface lists the refused orders; the integration-calls meter is the only trace *(design review D10)*
- **`gapCount` is a lower bound** — the switch's acknowledgement counts the coverage-gaps read (stock, open PO lines, open ASNs); a blind receipt, or an order of goods with no stock or open document anywhere, is refused without having been a gap, hence the "known gaps" copy *(design review D9)*
- **The switch is read at replay, licences are judged at the scan date** — a handheld receipt's licence phase runs when the op REPLAYS (it reads the switch then) but judges coverage on the scan's `occurredAt`. A scan made offline while enforcement was off and replayed after an owner turned it on is refused (into `grn.licence-refused`, waivable), although the floor scanned under the old rule *(code review, 2026-10-20)*
- **The order's phase-3 goods-attribute re-read is `FOR KEY SHARE`** — `lockSkuStatusesInTx` re-reads `food_category` / `drug_schedules` under the same lock as status, which a plain attribute UPDATE (`NO KEY UPDATE`) does not conflict with: an edit that commits after the re-read is not seen, so an order can commit against the attributes a moment before they changed *(code review, 2026-10-20)*
- **The concurrent first-PUT `conflict` arm is untested** — two first-ever `PUT …/licence-policy` racing both see no row; the tenant unique index lets one insert win and the other answers 409 `conflict`. No race test (the parked-waiter pattern) drives it *(code review, 2026-10-20)*

- **No retention for resolved entries** *(9-2 design)* — every source occurrence leaves a row forever, resolved ones included (and tombstones). - **No deep links from an audit row's target** *(9-3a design review #5)* — the Target column is the type plus an id tail, as plain text. The list pages the targets would land on are filtered by the active warehouse, not the target's (`/outbound` reads the active one), so a link would open the wrong list; each target type needs a route that takes its id and warehouse
- **No portal audit read, and no `client_id` on `audit_events`** *(9-3a design, Never list)* — the trail is the operator's, owner-only. A client cannot see who acted on its goods, and the table cannot be filtered or RLS-scoped by client. A portal read needs a `client_id` stamp on each row (derived from the target, the 21-2b rule) and the two portal layers (IMPLEMENTATION-GUIDE §7e)
- **Action names are inconsistent** *(9-3a design)* — the vocabulary grew story by story: `channels.disconnected` (plural subject), `sku.client-corrected` (hyphen), `count.variance.resolved` (three segments), the audit `purchase_order.created` beside the outbox `po.created`. 9-3a renames nothing (the trail is history) and new actions use `<subject>.<verb>` with `_`. A prefix filter therefore needs to know each module's spelling; an alias table in the read, or a documented vocabulary, would close it
- **Unkeyed system writers are outside the audit rule** *(9-3a design)* — the rule covers commands that write `idempotency_keys`. Sweeps and schedulers (the replenishment sweep, the expiry scan, the count scheduler, the wave cutoff sweep), sign-in, badge-in and push registration write no key, and only some of them audit. Which system actions an owner must see is a decision nobody has taken; the guard cannot see them
- **The trail starts at 9-3a** *(9-3a design, no backfill)* — about twenty keyed commands (transfers, POs, vendors, SKU edits, products, kits, imports, warehouses, zones, bins, registration, GRN submit, counts, device enroll) wrote no audit row before it. Earlier actions of those kinds are not in the trail and cannot be reconstructed with a trustworthy actor

### audit export (9-3b)

- **A download is not audited** *(9-3b design, Never list)* — fetching an export's file writes nothing. Who downloaded the trail (and when) is not in the trail. Recording it means an unkeyed audit row on a GET — outside the audit rule as written — and a decision on whether a re-download is a new event
- **Postgres storage until S3** *(9-3b human decision 1)* — the gzipped bytes live in `audit_export_files` (`bytea`) behind the `AuditExportStore` port. 9-3c did **not** change this store (its Never list: no change to the 9-3b export store, no signed URLs, no S3 read path for downloads — the WORM port is for ledger anchors only); a later story's object storage (and signed URLs, and the ledger digest + WORM anchor in the export) replaces the `PostgresAuditExportStore` binding; nothing else changes. Until then the bytes ride the database's backups and its size
- **The whole file is held in memory while it is written** *(9-3b design)* — the runner streams rows through `zlib.createGzip` into an in-memory buffer, and the download serves the stored buffer whole. **Measured 2026-10-14** (`bun scripts/loadtest-audit-export.ts`): 100,000 events → **3,412,846 bytes gzipped** (18.3 MB uncompressed), written in ~1.2 s. **At the 1,000,000-event cap** (`--events 1000000`, same day): **32,638,049 bytes gzipped** (182.6 MB uncompressed), written in ~50 s over 200 pages; the load script's single process (seed + server + runner + download) peaked at 1.58 GB RSS. Each running export holds its ~33 MB buffer (plus the page in flight), and each concurrent download the same. A streaming store (S3 multipart, a chunked bytea) would bound it
- **CORS does not expose `Content-Disposition`** *(9-3b design review #4)* — `app.factory.ts` sets no `exposedHeaders`, so a browser on another origin cannot read the server's filename; the web builds `audit-export-<IST yyyyMMdd-HHmm>.csv` from `requestedAt` itself. Exposing the header (and any other a client should read) is one CORS change, deliberately not made in 9-3b
- **No polling of the exports list** *(9-3b design)* — "Your exports" re-reads on Refresh, on a posted export, on a `#audit-exports` hash change and on an audit-export bell click; a `queued` row reads "Preparing…" until then. The bell is the completion signal
- **An export waits for as long as an older transaction stays open** *(9-3b code review #11)* — the §7d proof refuses to claim a `queued` export while any other client backend has a transaction that began before its `snapshot_at` (or while a session is hidden from the role — logged as `AUDIT EXPORT WAITING`). There is no deadline: a long backup transaction or a leaked idle-in-transaction connection keeps the row "Preparing…" until it ends. A maximum wait with its own failure reason (e.g. `snapshot-unprovable`) is the fix if it shows up
- **One export at a time per member, one claim per tick per tenant** *(9-3b design)* — the worker claims at most one export per tenant per tick, so many members exporting at once queue behind each other. Fine at owner-only volumes

## How to use this

1. **Before speccing a story**, read your module's section. A listed item with the fix already diagnosed is usually cheaper to fold in than to schedule separately.
2. **When a review defers something**, it lands in `deferred-work.md`, which is the authority. This file is a **hand-written digest** of it — no generator exists. When the two disagree, `deferred-work.md` wins; fix this file rather than the other way round.
3. **Epic retrospectives** are where open action items get claimed into a story or explicitly closed. *"Every open retro item claimed into a story spec or explicitly closed at the next epic boundary"* is itself an open process commitment *(epic-3 retro a11)*.
