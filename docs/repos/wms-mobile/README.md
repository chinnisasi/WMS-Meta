## Stack & structure (Story 3.2)

- Expo 57 / RN 0.87 with **Expo Router** (`app/` — the gate routes on the device phase: enrollment → badge-in → task inbox; full-screen revocation state). `bun` only.
- `src/scanning/` — the pure capture-agnostic decision engine: camera (`expo-camera`), HID keyboard wedge, and manual entry normalize to the same event; decisions are synchronous functions (rejection renders inside the 500 ms budget); rejected scans never queue.
- `src/offline/` — encrypted SQLite (WAL) offline store: every queued-op payload and secret is sealed AES-256-GCM under the enrollment-delivered offline-store key (pure-JS `@noble/ciphers`, byte-compatible with wms-be's `node:crypto` envelope — `v1:<iv>:<tag>:<ct>` base64 format); FIFO outbox + replay with client ULID idempotency keys (exactly-once), sync summary (settled / rejected / quarantined with session attribution). The unwrapped key lives in the device keychain (`expo-secure-store`), never in the database it decrypts.
- `src/state/device-store.ts` — the phase machine (unenrolled → enrolled → badged → revoked).
- a11y floor (UX-DR22): fill + glyph + word banner (never color-only), platform accessibility announcements, dynamic type honored (no `maxFontSizeMultiplier` caps), instant banner swaps under Reduce Motion, ≥48dp targets.
- Microcopy: verbs and numbers, no exclamation marks; the queue chip is amber depth, never red/error.

## Interface Contract (what this repo consumes from `wms-be`)

Keep this current whenever a cross-repo change lands.

- Base URL: `EXPO_PUBLIC_API_BASE_URL` (default `http://localhost:3000/api/v1`; inlined at bundle time). Hand-written API layer in `src/api.ts` (no codegen — the generated-client pipeline lives in wms-fe).
- Endpoints called (Stories 3.2–3.5 scope; all RFC 9457 problem+json, branched on machine-readable `code`):
  - `GET /api/v1/health` — boot check.
  - `POST /api/v1/tenants/{tenantId}/devices/enroll` (**unauthenticated**; `Idempotency-Key` ULID) `{code, label, pin}` → `201` `{device: {id, tenantId, label}, deviceToken, expiresInSeconds, offlineStoreKeySealed}` — the one-time enrollment-code redemption; the sealed offline-store key unwraps through the KMS boundary (dev builds mirror wms-be's sha256-stretched `DEVICE_ENCRYPTION_KEY`). Unknown/expired/already-redeemed code / wrong-tenant path → one indistinguishable `400 enrollment-code-invalid`; pin shape 4–6 digits → `400 validation-failed`; same-key replay re-serves the credential.
  - `POST /api/v1/tenants/{tenantId}/devices/badge-in` (Bearer **device token**) `{operatorEmail, pin}` → `200` `{accessToken, tokenType, expiresInSeconds, operator: {id, email, role}, device: {id, label}}` — mints the revocable operator-bound device session; first-ever badge-in needs connectivity, afterwards the device restores from its sealed cache (UX-DR6). Wrong operator/PIN → indistinguishable `401 badge-invalid`; unknown/revoked device → `403 device-revoked`.
  - `POST /api/v1/tenants/{tenantId}/devices/self-test/echo` (Bearer **badge-in session**; `Idempotency-Key`) `{payload}` → `200` `{deviceId, operatorUserId, echoed, receivedAt}` — the substrate's replay target. `401 unauthenticated` on a bare (badge-in-less) device credential; `403 device-revoked` / `403 role-denied` per command (device status + operator role re-read from the DB on every call — the token is transport, never authority).
  - `GET /api/v1/tenants/{tenantId}/devices/catalog-snapshot?warehouseId={warehouseId}` (Bearer **badge-in session**) → `200` `{generatedAt, warehouseId, skus: [{id, code, name, barcode, uom, batchTracked, serialTracked}], openPurchaseOrders: [{id, code, warehouseId, vendorId, lines: [{id, skuId, orderedQty, receivedQty, openQty}]}]}` — the sealed offline decision surface (AD-4): captured at cache time, the device decides against it offline and the server re-gates at replay. `404 warehouse-not-found` on a warehouse outside the tenant.
  - `POST /api/v1/tenants/{tenantId}/receiving/goods-receipts` (Bearer **badge-in session**; `Idempotency-Key`) `{warehouseId, poId?, blindReasonCode?, occurredAt, lines: [{poLineId?, skuId, batchCode?, mfgDate?, qty}]}` → `201` `{goodsReceipt: {id, code, status: 'recorded', lines: [{poLineId, skuId, batchId, batchCode, qty, appliedQty, excessQty}], rejectedLines?}}` — the `grn.submit` op's endpoint (the op's ULID is the idempotency key). Blind receipts carry `poId: null` + a `blindReasonCode` from the fixed enum; within-open quantities apply immediately (`appliedQty`), the excess pends (`excessQty`) for review.decide. Rejected lines surface with machine reasons (`po-line-not-found` / `po-line-not-open`); batch codes are 1–64 non-whitespace chars, required for batch-tracked SKUs and forbidden otherwise.
  - `GET /api/v1/tenants/{tenantId}/devices/catalog-snapshot` — **story 3.5 extends it additively:** `bins: [{id, code, zoneId, zoneCode, type, capacity, blocked, systemOwned}]` (blocked/system bins stay in the payload so the device can reject a scan against them pre-queue) and `putawayTasks: [{grnId, grnCode, grnLineId, skuId, skuCode, batchId?, batchCode?, qty (remaining), suggestedBin: {binId, binCode} | null, rationale}]` — suggestions baked into the snapshot are advisory; the server re-derives and re-gates at placement. A pre-3.5 sealed cache without the two keys is normalized at the sealed-read boundary (`src/state/catalog-snapshot.ts` → `parseCatalogSnapshot` defaults both to `[]`; the inbox/putaway screens never see `undefined`); a refresh recovers the full shape.
  - `POST /api/v1/tenants/{tenantId}/putaway/placements` (Bearer **badge-in session**; `Idempotency-Key` = the op's ULID) — the `putaway.place` op's endpoint (story 3.5): `{warehouseId, grnId, grnLineId, skuId, batchId?, qty, toBinId, reasonCode?|null, occurredAt (device time), serials: null}` → `201` `{placement: {…, suggestedBinId, suggestedBinCode, reasonCode}}` — the placement snapshot, re-served on replay. The operator flow (`app/putaway.tsx` + `src/putaway/draft.ts`): task picker → SKU scan → qty → bin scan/enter with wrong-bin/blocked pre-checks against the cached snapshot → a required mismatch reason from the fixed enum when the scanned bin differs from the task's suggested bin (the enum is hand-mirrored in `src/putaway/draft.ts` — a drift guard rides with the deferred report story) (story 12-4: the mirror gains `bulk-asset` — the server requires it on every bulk-asset placement, which is never the suggested bin — with a parity assertion pinning the mirror to the server's full enum; the device pre-check itself has no bulk arm yet, recorded in PENDING) → confirm queues exactly one `putaway.place` op. Serial-tracked SKUs are refused at the SKU scan in v1 (the payload always carries `serials: null`, normalized to absent server-side); the server re-gates everything at replay — a stale queued placement after the Receiving bin drained → `422 insufficient-on-hand` → quarantine with session attribution.
  - `GET /api/v1/tenants/{tenantId}/devices/catalog-snapshot` — **story 4.3 extends it additively again:** `pickTasks: [{waveId, picklistId, picklistLineId, orderId, orderLineId, skuId, skuCode, skuName, binId, binCode, batchId?, batchCode?, qty, sliceSeq, walkSeq, stopCount}]` — every still-unpicked line of every `ready` picklist on a `released` wave in the warehouse, **in walk order** (`bins.code` ascending). The WHOLE walk rides the snapshot deliberately: that is what lets a wrong-bin scan name the next walk bin holding the expected SKU with no network call. The bin and batch each task names are the plan's **suggestion** — the server re-derives both at pick time. A pre-4.3 sealed cache without the key is normalized at the sealed-read boundary (`parseCatalogSnapshot` defaults `pickTasks` to `[]` alongside `bins`/`putawayTasks`); a refresh recovers the full shape.
  - `POST /api/v1/tenants/{tenantId}/outbound/picks` (Bearer **badge-in session**; `Idempotency-Key` = the op's ULID) — the `pick.record` op's endpoint (story 4.3): `{warehouseId, picklistId, picklistLineId, skuId, binId, qty, occurredAt (device time), serials: string[] | null}` → `201` `{pick: {…, binId/binCode (what was SCANNED), suggestedBinId/binCode, batchId/batchCode (server-re-derived FEFO), reservationCommitted, lineStatus: 'picked'}}` — re-served on replay. **No batch is ever sent.** The operator flow (`app/pick.tsx` + `src/picking/draft.ts`): walk picker → bin scan → item scan → (serials, one per unit) → confirm queues exactly one `pick.record` op. On-device rejections are **synchronous** pure resolvers over the sealed snapshot, so nothing that fails them ever queues: a wrong item names the SKU the line expects; a wrong bin names the **next stop on this walk holding that SKU** (`nextWalkBinFor` — bins carry no spatial data, so "nearest" means next-on-route; null when the walk carries none, and the reason then stands alone); blocked and system bins are refused outright. A bin that is *another stop of the same walk for the same SKU* is **not** rejected — it passes as off-plan, because the plan's bin is a suggestion. Server-side outcomes the device must handle: `422 insufficient-on-hand` (the bin drained before replay — nothing persisted, the key is unconsumed, so the op is re-recordable), `409` (already picked / wave not released / picklist not ready / order not accepted), `400 wrong-item`, `403 device-revoked|role-denied`.
  - `POST /api/v1/tenants/{tenantId}/outbound/picks` — **story 4.4 extends the same op additively (no new op type, no transport change):** the payload gains `reasonCode: string | null`, and `qty` may be **below** the task's quantity (down to `0`, the empty shelf) whenever a reason rides with it. The reason enum is hand-mirrored in `src/picking/draft.ts` (`SHORT_PICK_REASON_CODES` — `bin-empty|fewer-units-than-planned|damaged-units|stock-not-found|other`, same order as the server's); `reasonCode` **is** hashed into the server's idempotency payload (the reason is intent, unlike `binStateEpoch`), so re-using a key with a different reason is `422`, while a whole pick sending `null` hashes exactly as it did pre-4.4. The `201` snapshot gains `shortfallQty`, `reasonCode`, `reservationReleased`, `replanReservationId` and `replanned[]`, `lineStatus` may read `short`, and **`pick.id` is now nullable** — a zero-unit report writes no `picks` row server-side, so `PickRecordResponse.pick.id` is typed `string | null`. Everything that makes a short pick interesting (releasing the hold, re-granting the remainder, planning the alternate stop) happens **server-side at replay**, which is by definition online: AD-14 forbids an offline client granting new ATP and this client grants none. The re-planned stop arrives as an ordinary new task card on the next snapshot refresh. The operator flow (`app/pick.tsx` + `src/picking/draft.ts`): "Record a short-pick" in the ghost-button slot below confirm opens the arm — which requires a **scanned bin**, because the report is about a bin and `chooseBin` clears it — with a ±/typed stepper (digits only, updated on every keystroke so the field always shows what confirm will queue, inert at 0 and at one below the stop) and the fixed reason list. **Confirm stays closed until a reason is named**, because the server refuses a reasonless short pick and an offline device would not learn that until replay. Serial-tracked stops take one serial per **drawn** unit (`drawQty`), never per planned unit; shrinking the count trims the list. `settledNote` reports where the remainder went when the queue drains — the re-planned stop, or that the order ships short.
- Op types in the outbox (the FIFO replay set): `self-test.echo` (3.2), `grn.submit` (3.3), `putaway.place` (3.5), `pick.record` (4.3, carrying story 4.4's short-pick arm), `pack.execute` (10.7 — one op carries the WHOLE order's scans, because the pack is all-or-nothing server-side). **`pick.task` is deliberately never an op type** — `src/state/op-dispatch.test.ts` fabricates that string to prove the dispatch's exhaustiveness guard throws, and naming a real op that would turn the proof into a live dispatch.
- **Story 10-6 extends both surfaces additively (no new op type, no new endpoint):**
  - `GET …/catalog-snapshot` — each `skus[]` entry gains **`uomPrecision: number`** (decimal places the SKU's base UoM declares — 0 for every count unit, 3 for kg) and **`catchWeightTracked: boolean`** (handled by unit, priced by weight). The device parses both with additive defaults at the sealed-read boundary (`parseCatalogSnapshot` → `uomPrecision ?? 0`, `catchWeightTracked ?? false`), so a pre-10.6 seal reads as the whole-unit, no-weight-prompt behavior.
  - `POST …/receiving/goods-receipts` — a `grn.submit` line for a catch-weight-tracked SKU gains **`weightsGrams: number[]`** — exactly `qty` whole-gram entries (one per physical unit, in weighing order; the server refuses the line both directions when the count differs from `qty`, and refuses any weight outside 1–`MAX_HANDLING_UNIT_WEIGHT_GRAMS` = 1,000,000 g). A **non**-catch-weight line carries NO `weightsGrams` key at all — absent, never null (null-vs-absent is load-bearing: the server refuses weights on a SKU that is not catch-weight tracked, and an absent key keeps a pre-10.3 receipt's idempotency hash byte-identical). Quantities on measured SKUs ride the payload un-floored (`qty: 2.5` kg); a too-precise typed value is refused **on-device** with copy that byte-mirrors the server's `precisionRefusalDetail` (`src/lib/quantity-input.ts`), never rounded, so the replay can never disagree with what the operator was told.
  - Replay single-flight: `src/state/replay-gate.ts` — `deviceStore.replay()` shares one in-flight pass among concurrent triggers, and `enqueueOp` waits for an in-flight pass to write back before appending, so a scan decided mid-replay can no longer be deleted unsent by the outbox's `replaceOps` write-back.
- **Story 10-7 (the pack bench) extends both surfaces additively:**
  - `GET …/catalog-snapshot` — gains two additive arrays: **`packTasks: [{orderId, skuId, skuCode, skuName, pickedQty, catchWeightTracked}]`** (ONE per-SKU row per packable order — `accepted`, at least one picklist line, none planned, not wholly withdrawn; `pickedQty` is the base-unit picked total from the same grouped-`picks` roll-up the pack command verifies against, capped at 500 with whole-order truncation) and **`handlingUnits: [{id, skuId}]`** (every `active` unit, deliberately UNCAPPED — a cap would make the bench refuse a real case label offline as unknown, the queue-and-die hole the array exists to close; active-only self-prunes as units flip `packed`). The device parses both with additive defaults at the sealed-read boundary (`parseCatalogSnapshot` → `?? []`), so a pre-10.7 seal shows no Pack work and nothing crashes.
  - `POST /api/v1/tenants/{tenantId}/outbound/packs` (Bearer **badge-in session**; `Idempotency-Key` = the op's ULID) — the `pack.execute` op's endpoint (story 10.7): `{orderId, scanned: [{skuId, qty, handlingUnitIds?}], weightGrams?}` → `201` `{pack: {…, orderStatus: 'ready_to_dispatch', lines: [{orderLineId, skuId, skuCode, skuName, orderedQty, packedQty, shortfallQty, ledgerEventId}]}}` — the packing slip, re-served on replay under the same key (nothing re-packs; a new key against a packed order → `409`). **No `dimensionsMm` is ever sent** — the web surface keeps that arm. The operator flow (`app/pack.tsx` + `src/packing/draft.ts`): order picker (pack tasks grouped by order, queued orders filtered from the durable outbox) → count-driven accumulation (an item barcode counts one unit of a 0-precision non-CW SKU; a catch-weight SKU counts **unit labels** — a barcode scan on one is refused; a measured (precision > 0) non-CW SKU carries a **typed, precision-aware quantity** (10-6's grammar) — a barcode scan on one is refused, because a +1 scan can never reach a fractional pick) → optional parcel weight typed in kg, carried as whole grams → confirm queues exactly one `pack.execute` op when every SKU's count equals its picked total **exactly**. On settle, `settledNote` names the pack receipt in the sync summary (sku × qty lines, total units, optional weight) — a settled pack is never a bare count. On-device refusals are synchronous and worded the server's way: over-scan names both quantities (`pack-mismatch` copy), a duplicate label names the duplicate, a label of a non-catch-weight SKU is refused fail-closed, an unknown label is refused before it can queue (the server 404 stands as backstop), and `handlingUnitIds`/`weightGrams` are key-ABSENT, never null (the non-CW pack's hash stays byte-identical to its pre-10.3 shape). Stale-snapshot packs (order packed/cancelled, unit already packed since the seal) replay into the existing rejected bucket — no new codes.
- **Story 11-7 (mobile variant-aware picking) extends both surfaces additively — no new op type, no new endpoint, nothing sent that was not sent before:**
  - `GET …/catalog-snapshot` — each `skus[]` entry gains **`variantValues: Record<string, string> | null`** (the SKU's values on its attached product's declared variant axes; **null when the SKU is unattached**) and **`axes: string[] | null`** (declaration order — the order a variant label is read in), and each `pickTasks[]` entry gains **`kitParentSkuCode: string | null`** (the exploded kit component's parent kit SKU code via `parentLineId`; null for an ordinary line). All three are **display-only** — the device decides nothing on them, and `pick.record`'s payload is byte-identical to its pre-11-7 shape. Typed **optional** in `src/api.ts` (the `binStateEpoch` precedent: absent = a pre-11-7 seal, null = the server's "no"), with `parseCatalogSnapshot` deliberately untouched — the legacy-seal arm in `device-store.test.ts` pins a pre-11-7 seal passing through **by equality with the keys omitted**, never `undefined`-valued.
  - Display grammar in `src/picking/variant.ts`, pinned verbatim in `variant.test.ts`: `variantLabel` (axes in declaration order, `axis: value` joined with the web's ` · `, `—` for a missing value — mirroring wms-fe's `variantValuesLabel` so both clients read one product the same way), `describeSku` (`label (code)`, bare code when unlabelled, `''` for an unknown SKU), `verifiedAnnouncement` (**the variant leads** the post-scan banner — `{label} — {name} verified — confirm N unit(s)` / `scan N serial(s)`; unlabelled SKUs read today's exact strings) and `kitContext` (`from kit {code}`, else null). UX-DR28: the pick task header leads with the label at the largest type scale (the SKU code demoted beneath it) and carries the kit line; `verifyTaskSku` composes `describeSku` on **both** sides of a wrong-item rejection, so a wrong-variant scan names both variants — a stale cache degrades to the pre-11-7 prose exactly.
- **Banner state-truth (UX-DR24, closing epic-3 retro F-2, story 4.3):** green `✓ Accepted` means the **server** settled the op. An on-device pass still sitting in the outbox reads amber `↻ Recorded · queued` (`scanStates.queued.word` in `src/theme.ts`); putaway's bin-mismatch banner no longer uses the green state for an on-device decision, and the health screen keeps the amber fill but says `Checking` (it records nothing). A **rejected replay** is parked client-side with its badge-in session attribution and surfaced in the sync summary, and **replay continues past it** — one refused op never blocks the rest of the walk. There is no backend rejected-op table; Epic 5's story 5.5 adds the web review queue.
- Auth material held on device: the 30-day device token (enrollment), the badge-in session (revocable server-side — no refresh machinery), the operator email (cached for badge-in restore). Revocation surfaces as `403 device-revoked` on the next request → full-screen state + queued ops move to quarantine with session attribution.
- Queue replay semantics the backend guarantees: same key + same payload re-serves the original response (exactly-once); replay is re-authorized against device status + role at the server (AD-4) — a revoked device's remaining queue quarantines client-side.
