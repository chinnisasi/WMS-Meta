## Stack & structure (Story 1.2)

- NestJS 12 modular monolith (TypeScript 6, bun as package manager), api shell (`src/api/`) + jobs shell (`src/jobs/`), 13 spine module folders under `src/modules/` per ARCHITECTURE-SPINE.md §Structural Seed: tenancy, catalog, inventory, inbound, putaway, outbound, movements, replenishment, channels, compliance, reporting, carriers, notifications. **Tenancy owns the first tables** (`tenants`, `users`, `warehouses`, `zones`, `bins`, `idempotency_keys` — all uuidv7 PKs with `tenant_id` stamped on every row); **catalog is the second real module** (story 1.4: `skus`, `uom_conversions`, `catalog_imports`, `catalog_import_errors`); other spine modules are still stubs.
- Modules own their tables exclusively and talk via interfaces/domain events — the tenancy command services (registration, sign-in, warehouse create) are the command-layer precedent: validate → hash → write → emit domain event through the seam (`LoggingEventBus`, `EVENT_BUS` token).
- Shared primitives in `src/shared/`: UUIDv7 ids, ULID idempotency keys, ISO-8601 UTC timestamps, integer paise, base-UoM integer quantities, GST basis points, cursor pagination, RFC 9457 problem-details (machine-readable `code`), idempotency/event-bus/outbox seams. The `Database` DI provider (`DATABASE` token in SharedModule) is a lazy proxy — boot never requires `DATABASE_URL`; the first query connects.
- **Two database connections (review loop 1 decision):** besides the scoped `DATABASE` connection there is an `AUTH_DATABASE` connection (`createLazyAuthDatabase`, `DATABASE_AUTH_URL` env, falling back to `DATABASE_URL`). It exists because the fail-closed RLS policies hide **all** rows from a non-superuser role with no `app.tenant_id` set — which sign-in and the registration replay lookup need (they run *before* any tenant context exists). The `DATABASE_AUTH_URL` role **must carry `BYPASSRLS`** (no tenant scope is safe or intended at auth time); `AUTH_DATABASE` is used **only for reads** by `sign-in.command.ts`, the replay lookup in `registration.command.ts`, and the outbox relay's tenant-discovery query (`src/shared/events/outbox.ts`, story outbox-relay) — never for writes (writes always go through the scoped `DATABASE` transaction with `setTenantScope`). In dev/CI it falls back to the superuser `wms` user (a boot-time warning fires on fallback). **Role provisioning:** `scripts/provision-roles.sql` creates the mandated pair — non-superuser `wms_app` for `DATABASE_URL`, non-superuser `BYPASSRLS` `wms_auth` for `DATABASE_AUTH_URL` (BYPASSRLS bypasses policies but not grants, so it also gets table grants). The e2e suite provisions its own `wms_auth_probe` role and points `DATABASE_AUTH_URL` at it, so sign-in/replay are exercised under RLS-binding conditions, not the superuser fallback.
- **Drizzle + RLS gap:** drizzle-orm 0.45.2 cannot model RLS in the schema (no `enableRLS`; `pgPolicy` would emit conflicting `CREATE POLICY` against the hand-written DDL), so the drizzle snapshot says `isRLSEnabled: false`. RLS DDL lives **only** in migration SQL — never rely on drizzle-kit for RLS; carry the DDL in migrations by hand.
- Drizzle (0.45.2) migrations on Postgres (`drizzle/`, runner `bun run db:migrate`, needs `DATABASE_URL`; dev DB via the repo's `docker-compose.yml` — postgres:18-alpine on host port 55432, user/password/db `wms`).
- **Multi-tenancy mechanism:** every table carries `tenant_id`; the app sets it per transaction via `select set_config('app.tenant_id', $1, true)` (see `src/shared/db/tenant-scope.ts` — moved there in story 1.4 so every module shares the `TenantTx` helper) and Postgres RLS is enabled with `USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)` policies on all tenant-bearing tables (migration `0001_greedy_scarecrow.sql` for the tenancy set — tenants, users, warehouses, idempotency_keys — and `0003_good_ulik.sql` / `0004_previous_otto_octavius.sql` / `0005_colorful_dreaming_celestial.sql` / `0006_*.sql` / `0007_pretty_silver_samurai.sql` for the later tables — audit/ledger/outbox included). **The empty-string NULLIF is load-bearing** — PG 18's `current_setting(..., true)` returns `''` (not NULL) after a transaction-local value expires, and a bare `''::uuid` cast throws. **Caveat: RLS is defense-in-depth only for non-superuser roles** — the docker-compose `wms` user is a superuser and bypasses RLS even with FORCE; the deployed app role must be a non-superuser (verified by the `wms_rls_probe` e2e test).
- **Idempotency:** real storage landed in the tenancy module (`idempotency_keys`: unique `(tenant_id, key)`, payload hash, response snapshot). Replays are de-duped **in the same transaction** as the write; same key + same payload replays the original response, same key + different payload → `422 idempotency-key-reuse`. The payload-hash fingerprint covers **`{name, ownerEmail}` only — never password material**: the raw password would make a leaked idempotency row an offline password oracle, and the scrypt hash is salted (random per call), so it is not replay-deterministic. Registration (no tenant context yet) looks up by key alone on `AUTH_DATABASE` and stamps the new tenant id on the row; a foreign replay fails the hash comparison and 422s, so nothing leaks. Concurrent same-key requests are arbitrated by the unique index — the 409 `conflict` handler wraps the idempotency-row INSERT itself. **Indexing:** besides the unique `(tenant_id, key)` index there is a plain `idempotency_keys(key)` index (migration `0002_misty_romulus.sql`) — the registration replay's key-only lookup runs on a table that grows on every mutating request. Registration orders its work **fingerprint → replay lookup → scrypt hash** so a replay never pays the ~100 ms hashing cost.
- **Transactional outbox (story outbox-relay, PR #9 — replaces the old post-commit publish):** every domain event is now an in-transaction append to `outbox_messages` (migration `0007`: uuidv7 id, `tenant_id`, `type`, jsonb `payload`, business-time `occurred_at`, `status pending|quarantined` enforced by a CHECK, `attempts`, `next_attempt_at`, `last_error`; fail-closed `tenant_isolation` RLS hand-appended) — the event commits or rolls back **with** the write that produced it (AD-7). Suppression is structural: commands reach `append` only on the fresh-write path, so an idempotent replay writes **no** second row (this closes epic-1 retro item 3 — `users.command.ts` previously re-published on replay). `PostgresOutboxSink.append(tx, message)` is the write side (`OUTBOX_SINK` token); `PostgresOutboxRelay.drain(limit)` the read side. **Relay mechanics:** one `drain` call = one cycle — session-level advisory lock (`wms:outbox-relay`) serializes relay instances (a concurrent cycle sheds → `[]`, AD-17), tenant discovery reads due tenants oldest-first on `AUTH_DATABASE` (the sanctioned second cross-tenant read, read-only), each tenant drains in `(created_at, id)` order inside its own `withTenantTransaction`, publishes through the existing `EVENT_BUS` seam (`LoggingEventBus` unchanged — logs type/tenant/eventId, never payloads; the outbox row id **is** the relayed `eventId`), and deletes the row on ack — **at-least-once** (a crash between publish and ack re-publishes; consumers own exactly-once effect, AD-5). Failures retry with backoff `min(2^(attempts-1)·5s, 5min)`, quarantine after 5 attempts (DLQ), and rows skip instead of aborting the cycle (per-tenant/per-row fault isolation). **Delivered rows are deleted** (delete-on-ack — events derive from committed state). **Worker:** `OutboxRelayWorker` in `src/jobs/` polls `drain(100)` — env-gated OFF unless `OUTBOX_RELAY_POLL_MS` (positive-integer ms, e.g. `2000`; `0`/unset = off; a non-integer fails the boot loudly) is set — **every deployment that wants delivery must set it** (`.env.example` carries `2000`). **Operator DLQ replay:** quarantined rows re-drain only via `OUTBOX_OPERATOR_REPLAY_SQL` (exported in `src/shared/events/outbox.ts`): `UPDATE outbox_messages SET status='pending', attempts=0, next_attempt_at=now() WHERE id=$1 AND status='quarantined'`. **Event coverage:** all 11 event types across the 9 emitting files ride the outbox (tenancy: `tenant.registered`, `user.invited/role_changed/accepted`, `warehouse.created`, `zone.created`, `bins.generated`, `bin.blocked`; catalog: `catalog.imported`, `catalog.sku_edited`; inventory: `stock.adjusted`, `ledger.chain_broken` — the severity-1 alert now appends in its own small tenant transaction and a failed append **rejects `verifyChain`** instead of being swallowed). `test/outbox.spec.ts` observes rows + delivery (first event-observation tests in the repo); `test/outbox-worker.spec.ts` pins the worker.
- **Continuous replay-reconciliation (Story 2.2, PR #10):** a sheddable `ReconciliationWorker` (`src/jobs/jobs.module.ts`, mirror of the relay worker — env gate `OUTBOX_RECONCILE_POLL_MS` with the same conventions, in-process shed, `unref`'d timer, shutdown hook) drives per-(tenant, warehouse) cycles through `InventoryFacade.reconcileNext()`: **one partition per tick, oldest-checkpoint-first** (discovery reads `ledger_events` heads vs `reconciliation_checkpoints` on `AUTH_DATABASE` — the sanctioned third cross-tenant read, read-only). Each cycle: detection in **one repeatable-read tenant transaction** (checkpoint validation `last_seq ≤ head` — invalid twice in a row → discard + `reconciliation.checkpoint_invalid` outbox alert + full replay; a clean pass advances the checkpoint in the same snapshot; the compare window is bounded to the (sku, bin) scopes touched by events in `(last_seq, watermark]`, so a movement committing mid-cycle is the next cycle's problem, never a false positive), then — on divergence — a **repair transaction under the append path's per-warehouse advisory lock** (`rebuildProjectionsInTx` re-folds fresh so concurrently-committed movements are included, not clobbered) that also quarantines repeats and appends the `reconciliation.divergence` alert in the SAME commit (rebuild + alert always travel together; first divergence = rebuild + alert, a repeated divergence within the window = quarantine + re-alert; quarantine is a durable `inventory_quarantines` row — one open row per scope via a partial unique index — that Story 2.3's reservation path will consume). **New tables (migration `0008_lowly_khan.sql`, hand-appended fail-closed RLS + CHECKs, same 0007 pattern):** `reconciliation_checkpoints` (unique `(tenant, warehouse)`; `last_seq`, `invalid_attempts`, plus `last_divergences` jsonb — the story spec listed only the first two; the third is the implementation's repeat-detection memory: scopes flagged by the previous non-advanced pass) and `inventory_quarantines` (`status` CHECK `open|resolved`, `from_seq ≤ to_seq` CHECK). **Verify-before-anchor:** `anchorChain` runs `verifyChainInTx` over its range inside the anchor transaction and commits nothing over a broken range (returns the `ChainBreakReport`; the severity-1 `ledger.chain_broken` alert path is unchanged). `LedgerService.rebuildProjections` is the derived-state repair entry (the architecture test still pins stock_on_hand writes to `ledger.service.ts` alone); `InventoryFacade.reconcile/reconcileNext/rebuildProjections` are background/operator surfaces — **no new HTTP route, no OpenAPI change**. `test/reconciliation.spec.ts` covers the I/O matrix end to end.
- **Batch & serial traceability (Story 2.4, PR #13):** catalog gains batch/serial **identity** — `batches` (unique `(tenant, sku, code)`, mfg/expiry dates) and `serials` (unique `(tenant, sku, serial_number)`) tables, ensured idempotently through `CatalogFacade.ensureBatches`/`ensureSerials` (migration `0010_sharp_hardball.sql`, drizzle base + hand-appended fail-closed RLS + CHECKs + traceability indexes on `ledger_events(tenant_id, serial_ref, seq)` / `(tenant_id, batch_ref, seq)`). The ledger opens the reserved batch/serial arms on `stock.adjusted`: inventory gains the `batch_on_hand` projection (unique `(tenant, warehouse, sku, bin, batch)`) folded in the **same transaction** as append — and by replay / reconcile-scan / rebuild (the architecture test's single-projection-path pin now covers it); serial location is derived from the serial's latest ledger event; duplicate-scan/wrong-bin draws fail at ledger-write time (`409 duplicate-serial` naming the location). Serial-tracked movements are **one ledger event per serial unit** (N qty ±1 events, one idempotency record). Concurrency: per-serial tenant-wide advisory locks (keyed `tenant:serial:ref`) acquired in sorted order before the warehouse lock — no lock-order inversion. FEFO (CHECKPOINT 1): the api layer composes batch identity + FEFO resolution (catalog expiry × inventory batch-on-hand join, oldest non-expired with stock in the bin, expiry ASC nulls-last); the composition never sees a retry — **replay beats composition** (the command-owned fingerprint pre-check returns the stored snapshot even when the FEFO batch has since been exhausted); arms are normalized (null = absent, serials trimmed, empty array absent) before identity AND fingerprint; `stock.adjust` is asserted before any validation 400 or identity creation. Blocked/QC lifecycle (`status` columns) ships schema-only until Epic 3/4.
- **Inventory read surfaces (Story 2.5, PR #14):** the 2.1–2.4 facade reads go HTTP (additive, reads only — no migrations, no writes, no capability gating, no drizzle changes): a **paginated stock list** (`InventoryFacade.listStock` — plain `stock_on_hand` rows, keyset cursor exactly like `listEvents` with `decodeCursorSafe`, optional `skuId`/`binId` filters — tracked and untracked SKUs alike, no batch fields), the **FEFO batch list** and **batch/serial detail** (api-layer composition, the 2.4 precedent: catalog owns identity via tiny `CatalogFacade.findBatch`/`findSerial` existence reads + `getBatches`, inventory owns state via `batchOnHand`/`batchBinsOnHand`/`serialLocation`/`serialHistory` — neither facade imports the other; unknown/malformed identity → **404 via the existence check before any detail query**, the CHECKPOINT 1 semantics), and the **timeline's additive nullable passthroughs** (`batchRef`/`serialRef`/`referenceDoc` — each event carries its reference document verbatim, serving the ≤2-navigations contract with zero extra queries; legacy arm-less events serialize identically apart from the new null fields). The adjustments endpoint's failure surface is documented in OpenAPI (closing the 2-4 review deferral: the 400 arm violations, 409 `duplicate-serial`/`serial-elsewhere`, 422 `insufficient-on-hand` naming the resolved batch's on-hand). **No ATP HTTP route** (deferred to Epic 4, CHECKPOINT 1); reservations stay facade-only. The batch list is deliberately unpaginated (finite per-SKU identity rows; only the stock list pages). `test/inventory-surfaces.spec.ts` covers the I/O matrix (8 tests, advisory lock 742106).
- **Inbound module — vendors + the PO lifecycle (Story 3.1, PR #15):** the `inbound` spine module stops being a stub: the purchase-order truth that receiving (3.3) will consume. **New tables (migration `0011_tiresome_wraith.sql`, drizzle base + hand-appended fail-closed RLS `*_tenant_isolation` policies + CHECKs, the 0005→0010 pattern):** `vendors` (unique `(tenant, code)`, `name`, `is_default`), `purchase_orders` (unique `(tenant, code)`, `vendor_id`/`warehouse_id` uuid columns — POs are **warehouse-scoped**, validated in-command via `assertWarehouseInTenant` → `404`; `status` CHECK `open|closed`; `carried_from_po_id` for the successor chain), `purchase_order_lines` (`ordered_qty` > 0, `received_qty` ≥ 0 defaulting **0 until 3.3 receipts land**, `unit_cost_paise` ≥ 0 (AD-9 paise), `expected_date`, line `status` CHECK `open|cancelled|carried`; the `received_qty ≤ ordered_qty` CHECK is deliberately deferred to 3.3's over-receipt-approval decision). **No FKs, no ledger writes** — a PO is not stock; `openQty = ordered − received` is always derived, never stored. **Commands** (`VendorCommand.create`, `PurchaseOrderCommand.create/amend/close`) run the established invariant order (role re-eval → idempotency replay → asserts → write → in-tx outbox → idempotency-key snapshot). **Amend is full-line-set semantics**: lines with an `id` update in place, without one are added, absent ones removed — `≥1` line enforced (`400` on `[]`), a repeated line id → `400`, unknown line id → `404`; `received_qty` is never in the update set; the PO row locks `FOR UPDATE` (concurrent amend/close serialize, the loser sees `409 po-not-open`). **Close is total** (one disposition per line — missing → `400`, duplicate → `400`, unknown → `404`); `carried` moves `ordered − received` to **ONE successor open PO** (same vendor/warehouse, code `${original}-C{n}` first free n, `carriedFromPoId` set, received restarting at 0); all-cancelled → no successor (`successor: null`); received quantities are never touched by close. **Outbox events** (inline literals, full post-mutation snapshot payloads): `vendor.created`, `po.created`, `po.amended`, `po.closed` (`payload.successor` carries the successor when one was created).

- **Real-time ATP & atomic reservations (Story 2.3, PR #12):** Valkey 9.1 (docker-compose on host port **56379**, `VALKEY_URL` env, `src/shared/valkey/` — `ValkeyClient` wraps two pre-declared-keys Lua scripts in `reservation-scripts.ts`: **grant** (ready-marker gate → counter-exists gate → nil guard → ceiling check → `INCRBY` + `EXPIRE`) and **release** (floored-at-0 `DECRBY` with `KEEPTTL`)) is the **atomic-decision store only — never the truth**. Keys are tenant-namespaced and hash-tagged: `wms:{tenantId}:wh:{warehouseId}:res:{skuId}` (+ `…:res:__ready__`), so a single warehouse's reservations live on one Redis cluster slot. Postgres gains the `reservations` journal (migration `0009_overjoyed_sway.sql`, hand-appended fail-closed RLS + CHECKs incl. positive-quantity and `state held|committed|released|expired`) as the durable truth, on the same 0008 pattern. **Model:** the Valkey counter holds *reserved* quantity (commit leaves the counter untouched — ATP loss transfers to the pick path in later epics); terminal transitions are conditional UPDATEs on the journal (one winner), then the release script floors the counter at 0. **Corruption recovery:** `rebuildReservationCounters` disarms (deletes `__ready__`) → seeds counters from a journal sum → disarms-corrects-arms again; grant Lua fails **closed** (`503`) while `__ready__` is missing or the counter is unreadable. A boot-time rebuild runs on `onModuleInit` (failure logs and keeps grants failing closed until a later rebuild succeeds). **Divergence detection = scheduled parity pass** (human decision at review loop 1): every reaper cycle compares each live scope's counter vs its journal sum (`held|committed`) on `BYPASSRLS` `AUTH_DATABASE` (the sanctioned fourth cross-tenant read, read-only) and rebuilds the warehouse on any mismatch; failures log and wait for the next cycle. **Expiry:** `ReservationService.expireDueReservations` (driven by a sheddable `ReservationReaper` in `src/jobs/`, env gate `RESERVATION_REAPER_POLL_MS` with the same conventions as the other workers — `.env.example` carries `2000`, and **every deployment must set it or holds never expire**) settles due holds in the journal, per-hold fault isolation, then runs the parity pass. **Facade surface (no HTTP):** `InventoryFacade`/`ReservationService` expose `grantReservation` (returns the held row; `409 unavailable` deterministic loser, `503` fail-closed on Valkey down; same-quantity replay re-serves the held row, **different-quantity replay → 409 conflict** — human decision at review loop 1), `commitReservation`/`releaseReservation` (terminal, idempotent by state — released/expired rows answer 409/404-shaped deterministic errors), `atp` (= max(0, onHand-with-quarantine-excluded − reserved − qcHeld − buffer)), `rebuildReservationCounters`, `expireDueReservations`. Validation hardening: UUID-shaped tenant/warehouse/sku/reservation ids (400), positive-integer quantity, `ttlSeconds` ≤ ~10 years. **Story 2.3 adds NO HTTP surface and NO OpenAPI change** — the FE contract is unchanged; order wiring consumes these facade methods in Epic 4.
- **Sessions:** 15-minute HS256 JWTs hand-signed with `node:crypto` (`src/modules/tenancy/jwt-session.ts`; claims `sub` + `tenant_id`, `exp` ≤ 900 s) — no refresh tokens. The signing secret is `JWT_SECRET` (≥ 16 chars, required at sign-in/verification time). Passwords are scrypt hashes via `node:crypto`.
- **Zero-warehouse invariant:** `TenancyService.requireActiveWarehouse(tenantId)` throws `422 no-active-warehouse` — Epic 2 consumes this before any stock write.
- **Warehouse-scoped master data (Story 1.3):** `zones` and `bins` are the first tables to carry `warehouse_id` alongside `tenant_id`. **Warehouse ownership is app-layer** — `assertWarehouseInTenant(tx, tenantId, warehouseId)` (in `tenancy.service.ts`) runs inside the command transaction before any zone/bin write and answers foreign/nonexistent warehouses with `404 not-found`; **RLS stays single-dimension** (`<table>_tenant_isolation` on `tenant_id` only, hand-written DDL in migration `0003_good_ulik.sql`) — composite (tenant + warehouse) policies are rejected. - **Grid generator (Story 1.3):** `BinCommand.generateGrid` mass-creates bins from an aisle-letter range (A–Z ascending) × bays × levels, zero-padded `A-01-01` codes, **capped at 500 bins per run** (`422 grid-too-large` above). One `withTenantTransaction`, one idempotency record — all-or-nothing; a collision pre-check in the same transaction fails the run naming the first conflicting code with nothing committed (`409 duplicate-bin-code`), and a same-key replay re-serves the stored snapshot.
- **Setup checklist (Story 1.3, catalog step wired in 1.4):** `GET /tenants/{tenantId}/setup-checklist` is **computed on read** — no stored step rows. Steps: `warehouse` (done at ≥1 warehouse), `bins` (done at ≥1 bin), `catalog` (story 1.4 — done at ≥1 SKU; `CatalogModule` is imported by `TenancyModule` and the step aggregates through `CatalogFacade.getImportSummary`, the first cross-module facade consumption: detail reads `Done · N SKUs · last import X committed, Y failed`, and stays honest when a tenant has import history but zero committed SKUs), `users` (wired in story 1.5 — done at ≥1 invited team member, see the Story 1.5 bullet below). Each step carries `key`, `label`, `done`, `detail`, `href` (deep link, `/settings` today).
- **Catalog module (Story 1.4):** owns `skus` (unique `(tenant_id, code)` and `(tenant_id, barcode)` per tenant), `uom_conversions` (unique `(sku_id, uom)`, positive-integer factors relative to the base UoM), `catalog_imports` (run ledger), `catalog_import_errors` (row-level rejections) — migration `0004_previous_otto_octavius.sql` with hand-written fail-closed RLS on all four (same `tenant_isolation` pattern, no FKs). **The import is synchronous multipart CSV/XLSX** (≤ 10,000 data rows, ≤ 5 MB): valid rows commit in **one transaction** and bad rows are returned per row `{rowNumber, skuCode, code, detail}` — partial commit is honest, a `201` can carry failures. Duplicate SKU codes / barcode collisions are **row-level** rejections naming the conflict (`duplicate-sku-code` / `duplicate-barcode`) when the conflicting row is already committed before the run starts. A `409` can still fail a **whole import** in two transient races: a concurrent import introducing the same SKU code / barcode (the pre-check passes, the row insert hits the unique index — retry re-runs the row-level checks), and concurrent imports sharing one Idempotency-Key (the loser's idempotency-row INSERT hits the unique index → `409 conflict`, same arbitration as registration). Fix mode (`mode=fix`) is **set-membership against the latest run**: only rows whose SKU code appears in that run's `catalog_import_errors` are processed; everything else counts `skippedRows` and is untouched — a clean fix run leaves an empty set, so the next fix round skips everything. There is **no manual SKU create** — catalog entries enter only through import, then are edited via PATCH (the SKU code is immutable). Barcodes are generated server-side (uuidv7) unless the file provides one. The import payload fingerprint is **sha256(file bytes) + mode** — a replay re-serves counts + error list; a different file on the same key is `422 idempotency-key-reuse`. File-level failures: `415 unsupported-file-type` (not .csv/.xlsx), `400 file-unreadable` (garbage bytes, unknown/missing header columns, header with no data rows), `422 import-too-large` (row cap, byte cap — multer's `LIMIT_FILE_SIZE` arrives as a 413 `PayloadTooLargeException` and the route-scoped `CatalogUploadFilter` translates it to `422 import-too-large` problem-details). GST is stored as **basis points** (0–10000); row validation order: shape → gst range → uom factor → duplicates. **The `EVENT_BUS` provider moved from TenancyModule to SharedModule** (`src/shared/events/event-bus.ts`) in this story — catalog is the first cross-module event emitter (`catalog.imported`, `catalog.sku_edited`), same post-commit guarded publish.
- **Users, roles, permission gating (Story 1.5):** the `users` table gains `role` (`owner|ops_manager|operator|accountant`, default `owner` for the registering user) and `status` (`invited|active`). **Authorization is per-command, DB-read based** — `getMemberRoleIn`/`getMemberRole` read the caller's current role **inside the command transaction** (the JWT carries only `sub` + `tenant_id`; it is transport, never authority), so a role change is effective on the caller's next command without re-login. The capability matrix lives in `src/modules/tenancy/permissions.ts`: `owner` holds all 8 capabilities (`warehouse.create`, `zone.create`, `bin.create`, `bin.block`, `catalog.import`, `sku.edit`, `users.invite`, `users.role_change`), `ops_manager` the six operational ones (no users.*), `operator`/`accountant` none — **reads are never gated**. Denials are `403 role-denied` naming the role and the missing capability. **Invites:** `POST /tenants/{tenantId}/users` `{email, role}` creates the user `invited` with a `DUMMY_HASH` password and returns `inviteToken` (raw base64url — its only durable stores are this response and the idempotency snapshot; only its sha256 hash lives on the users row) + 7-day `inviteExpiresAt`; there is no email delivery — the owner shares the one-time link out-of-band. A same-Idempotency-Key replay re-serves the original response (same token); a **fresh key** against an email that already belongs to any user of any tenant — `invited` or active, the pre-check has no status filter — is `409 email-exists`. **`POST /tenants/{tenantId}/accept-invite` is unauthenticated** `{token, password, tenantId}` (the tenantId is folded into the idempotency payload hash — a mismatched one is `invite-invalid`) → sets the scrypt hash, flips status to `active`, returns the user; the token is valid only on the inviting tenant's URL, and unknown/expired/burned tokens are one indistinguishable `400 invite-invalid` (one-time use, 7-day TTL — the accept UPDATE is itself conditional on the invite still being pending, so concurrent accepts cannot double-fire). An `invited` user attempting sign-in gets `403 invite-pending` for **any** password (the check runs before password verification, burning one scrypt round so timing does not leak account state). **Role changes:** `PATCH /tenants/{tenantId}/users/{userId}` `{role}`; demoting the **last owner** → `409 last-owner` with nothing persisted (a second owner unlocks it); every invite, role change, and accept writes an `audit_events` row (actor, action, target, reference). **`GET /tenants/{tenantId}/me`** returns the caller's own row (`{user}`) — the frontend bootstraps it on app mount so role changes surface without re-login. Sign-in's response now carries `user {id, email, role, status}` alongside the tenant. **RLS deepening:** `audit_events` (migration `0005_colorful_dreaming_celestial.sql`, same `tenant_isolation` pattern) and the users columns are covered by the fail-closed RLS policies; the e2e suite probes them with non-superuser roles (`wms_rls_probe` / `wms_auth_probe` — probe-role DDL is serialized across jest workers with `pg_advisory_xact_lock` to dodge Postgres `tuple concurrently updated` races). The setup checklist's `users` step is now wired (story 1.5): done at ≥1 invited team member, detail `Done · N team member(s) invited`.

## Interface Contract (what this repo provides to `wms-fe`)

Keep this current whenever a cross-repo change lands — this is what lets an agent catch "this backend change breaks the frontend" *before* making the change, not after.

- API base path / version exposed: `/api/v1` (document version 1.0.0)
- Endpoints offered (Story 1.1 + 1.2 + 1.3 + 1.4 + 1.5 scope): `GET /api/v1/health`, `POST /api/v1/echo`, `GET /api/v1/openapi.json` (Swagger UI at `/api/docs`); plus the tenancy surface —
  - `POST /api/v1/tenants` `{name, ownerEmail, password}` → `201` tenant + owner user (no password material exposed). Requires an `Idempotency-Key` header (missing/malformed → `400`; key reuse with a different payload → `422 idempotency-key-reuse`). Owner-email uniqueness is **global** (one tenant per email); duplicate → `409 duplicate-email`. String inputs are **trimmed at the validation boundary** (`@Transform` in `tenancy.dto.ts`) — a padded `" a@b.com "` validates like its trimmed form, and whitespace-only fields fail `@Length`.
  - `POST /api/v1/tenants/sign-in` `{email, password}` → `200` `{accessToken, tokenType: 'Bearer', expiresInSeconds: 900, tenant, user: {id, email, role, status}}` (story 1.5 added `user`). Unknown email vs wrong password are indistinguishable → `401 unauthenticated`; an `invited` user gets `403 invite-pending` for any password.
  - `POST /api/v1/tenants/{tenantId}/warehouses` `{code, name}` → `201` warehouse; requires the sign-in JWT (`Authorization: Bearer`) **and** the path tenantId must match the token's `tenant_id` (mismatch → `403 permission-denied`); requires `Idempotency-Key`; duplicate code → `409 duplicate-warehouse-code` naming the code.
  - `GET /api/v1/tenants/{tenantId}/warehouses?cursor&limit` → `200` `{items, nextCursor}` (keyset pagination, same auth + tenant-ownership rules; `limit` is validated 1–200 → `400 validation-failed` outside the range).
  - Zones/bins surface (Story 1.3 — all require the sign-in JWT, the path `tenantId` must match the token's `tenant_id`, and all mutating routes require `Idempotency-Key`):
    - `POST /api/v1/tenants/{tenantId}/warehouses/{warehouseId}/zones` `{code, name}` → `201` zone. Foreign/nonexistent warehouse → `404 not-found`; duplicate code → `409 duplicate-zone-code` naming the code.
    - `GET .../zones?cursor&limit` → `200` `{items, nextCursor}` (keyset, limit 1–200, `400 invalid-cursor` on crafted cursors).
    - `GET .../zones/{zoneId}/bins?cursor&limit` → `200` `{items, nextCursor}` (keyset, limit 1–200, `400 invalid-cursor` on crafted cursors / `400 validation-failed` on out-of-range limit; foreign zone → `404 not-found`). Created bins are immediately listed — no dormant state.
    - `POST .../zones/{zoneId}/bins` `{code, capacity, type}` → `201` bin (immediately usable downstream — no dormant state). Duplicate code → `409 duplicate-bin-code` naming the code (unique per **warehouse**, across zones); foreign zone → `404 not-found`.
    - `POST .../zones/{zoneId}/bins/grid` `{aisleFrom, aisleTo, baysPerAisle, levelsPerBay, capacity, type}` → `201` `{warehouseId, zoneId, generatedCount, firstCode, lastCode}`; ≤ 500 bins (`422 grid-too-large`), one transaction + one idempotency record; any code collision → `409 duplicate-bin-code` naming the first conflicting code, **nothing committed**; same-key replay re-serves the same snapshot.
    - `PATCH /api/v1/tenants/{tenantId}/warehouses/{warehouseId}/bins/{binId}` `{blocked}` → `200` bin — the only bin edit in this story; unknown bin → `404 not-found`.
    - `GET /api/v1/tenants/{tenantId}/setup-checklist` → `200` `{steps: [{key, label, done, detail, href}]}`, computed on read (see above); session-guarded like the other tenancy reads.
  - Catalog surface (Story 1.4 — all require the sign-in JWT, the path `tenantId` must match the token's `tenant_id`; both mutating routes require `Idempotency-Key`):
    - `POST /api/v1/tenants/{tenantId}/catalog/imports` (multipart/form-data: binary `file`, optional `mode=initial|fix`) → `201` `{importId, mode, committedRows, failedRows, skippedRows, errors: [{rowNumber, skuCode, code, detail}]}` — **a 201 can carry failures** (partial commit, see the catalog bullet above). Row-level `code` values: `validation-failed`, `duplicate-sku-code`, `duplicate-barcode`. File-level errors: `400 file-unreadable`, `415 unsupported-file-type`, `422 import-too-large` / `idempotency-key-reuse`; missing file → `400 validation-failed`. Replay with the same key + file re-serves the exact snapshot; different file on the same key → `422 idempotency-key-reuse`. Documented header: `sku_code,name,uom,uom_conversions,gst_rate,hsn,batch_tracked,serial_tracked,reorder_point,reorder_qty,barcode` (first four required; `uom_conversions` entries look like `box:12;case:144`; `gst_rate` in basis points).
    - `GET /api/v1/tenants/{tenantId}/catalog/skus?cursor&limit` → `200` `{items: [{id, code, name, uom, gstRateBps, hsn, batchTracked, serialTracked, reorderPoint, reorderQty, barcode, uomConversions, createdAt}], nextCursor}` (keyset, limit 1–200, `400 invalid-cursor` on crafted cursors).
    - `PATCH /api/v1/tenants/{tenantId}/catalog/skus/{skuId}` (body fields all optional: `name, gstRate (basis points), hsn (string or null), batchTracked, serialTracked, reorderPoint, reorderQty, barcode`) → `200` SKU — the SKU `code` is not part of the contract (immutable; unknown fields rejected by the whitelist). Unknown SKU → `404 not-found`; barcode collision → `409 duplicate-barcode` naming the conflicting SKU's code; empty body → `400 validation-failed`. Same-key replay re-serves the snapshot; different payload → `422 idempotency-key-reuse`.
  - Users/roles surface (Story 1.5 — all require the sign-in JWT and the path `tenantId` matching the token's `tenant_id`, except accept-invite; **reads are open to every tenant member**, the two mutations are Owner-capability-gated `403 role-denied`; all mutating routes require `Idempotency-Key`):
    - `POST /api/v1/tenants/{tenantId}/users` `{email, role: 'operator'|'accountant'|'ops_manager'|'owner'}` → `201` `{user: {id, email, role, status: 'invited', createdAt}, inviteToken, inviteExpiresAt}` — the raw one-time token (sha256-hashed on the users row; the raw value also persists in the idempotency snapshot so a replay re-serves it), 7-day TTL; no email delivery, the owner shares the link out-of-band. A same-Idempotency-Key replay re-serves the original response; a fresh key against an email that already belongs to any user of any tenant (`invited` or active) → `409 email-exists`; non-owner caller → `403 role-denied` naming role + capability.
    - `GET /api/v1/tenants/{tenantId}/users?cursor&limit` → `200` `{items: [{id, email, role, status, createdAt}], nextCursor}` (keyset, limit 1–200) — open to every tenant member.
    - `PATCH /api/v1/tenants/{tenantId}/users/{userId}` `{role}` → `200` updated user — Owner capability `users.role_change`; demoting the last owner → `409 last-owner` (nothing persisted); unknown user → `404 not-found`. Effective on the target's **next command** (per-command DB role read) — no re-login.
    - `POST /api/v1/tenants/{tenantId}/accept-invite` **(unauthenticated)** `{token, password, tenantId}` → `200` `{user}` (status flips `invited` → `active`, scrypt hash set; the body tenantId is folded into the idempotency payload hash — mismatch → `400 invite-invalid`); the token is valid only on the **inviting** tenant's URL, and unknown/expired/already-used tokens → `400 invite-invalid`.
    - `GET /api/v1/tenants/{tenantId}/me` → `200` `{user: {id, email, role, status, createdAt}}` — the caller's own row; the frontend bootstraps this on app mount so role changes surface without re-login.
  - All error responses are RFC 9457 problem+json with machine-readable `code` and `instance`. Story 1.5 adds the codes `role-denied` (403), `email-exists` (409), `last-owner` (409), `invite-invalid` (400), and `invite-pending` (403).
  - Inventory surface (Story 2.1 — the append-only ledger core; all require the sign-in JWT, the path `tenantId` must match the token's `tenant_id`; the mutation requires `Idempotency-Key` and the `stock.adjust` capability — Ops Manager and Owner):
    - `POST /api/v1/tenants/{tenantId}/inventory/adjustments` `{warehouseId, skuId, binId, quantityDelta (signed base-UoM integer, non-zero), reasonCode, note, occurredAt? (Z-suffixed ISO-8601 UTC, defaults to commit time)}` → `201` `{event: {id, seq, type: 'stock.adjusted', skuId, binId, quantityDelta, occurredAt, recordedAt}, onHand: {skuId, binId, quantity}}`. Exactly one `ledger_events` row + the `stock_on_hand` projection in one commit. Errors: `400 validation-failed` (bad body / `occurredAt` / zero delta), `403 role-denied` (re-evaluated before the replay lookup — a demoted actor's replay denies even on a valid key), `404 not-found` (warehouse/bin/SKU scope), `409 conflict` (concurrent same-key), `422 idempotency-key-reuse`, `422 insufficient-on-hand` (names the bin and its current on-hand; nothing persisted). Same-key same-payload replays re-serve the snapshot with no second event.
    - **Story 2.4 arms (additive request fields on the same endpoint — batch/serial-tracked SKUs only; untracked passthrough unchanged; openapi diff is request-body-additive only):**
      - `batch?: {code, mfgDate?, expiryDate?, overrideReason?}` — batch intake (positive delta) **requires** `batch.code` and ensures identity idempotently (same code → same batch; dates optional but must be Z-suffixed UTC and `expiryDate ≥ mfgDate` → `400 validation-failed` otherwise; `overrideReason` on an intake → `400`). A draw (negative delta) on a batch-tracked SKU with `batch` omitted defaults to **FEFO** (oldest non-expired batch with stock in the bin, expiry ASC nulls-last; no eligible batch → `422 insufficient-on-hand`); naming an explicit batch is an **override** and requires `overrideReason` (`400` without) — the reason is recorded verbatim in the ledger event's reference doc. Over-draw beyond the named batch's bin quantity → `422 insufficient-on-hand` (api pre-check names the batch code; the ledger fold guard backstop names the `batchRef` uuid).
      - `serials?: string[]` (≤1000, trimmed at the boundary) — serial-tracked movements: `|quantityDelta|` must equal the serial count (`400`), duplicates within one request → `400`; a serial already located in another bin → `409 duplicate-serial` naming the location; one ledger event per serial unit in one transaction. `batch: null` / `serials: null` behave as absent; an empty `serials` array behaves as absent. Permission (`stock.adjust`) is asserted before any arms validation or identity creation; a same-key retry with different arms → `422 idempotency-key-reuse`.
  - **Story 2.4 adds NO new HTTP route** — traceability reads were facade-only in 2.4; story 2.5 exposes them (PR #14). New machine codes for the FE: `duplicate-serial` (409). New capability: none (`stock.adjust` gates the armed endpoint unchanged).

    - `GET /api/v1/tenants/{tenantId}/warehouses/{warehouseId}/inventory/stock?skuId&binId&cursor&limit` → `200` `{items: [{id, warehouseId, skuId, binId, quantity, createdAt}], nextCursor}` — the on-hand projection (keyset cursor, limit 1–200; `400 invalid-cursor`; foreign warehouse → `404`).     - `GET /api/v1/tenants/{tenantId}/warehouses/{warehouseId}/inventory/batches?skuId&binId` → `200` `{items: [{id, code, mfgDate, expiryDate, status, quantity}]}` — FEFO order (expiry ASC nulls-last, expired batches still listed — order is data, not policy), on-hand 0 when none, the `binId` filter narrows the quantity half of the join. `skuId` omitted/malformed → `400 validation-failed`; unknown `skuId` → `200 {items: []}` (filters narrow; only path resources 404). Unpaginated (finite per-SKU batch identity).
    - `GET /api/v1/tenants/{tenantId}/inventory/batches/{batchId}` → `200` `{id, skuId, code, mfgDate, expiryDate, status, bins: [{warehouseId, binId, quantity}], history: [{warehouseId, seq, type, skuId, quantityDelta, fromBinId, toBinId, serialRef, occurredAt, recordedAt, eventHash}]}` — per-bin on-hand across every warehouse of the tenant, full history oldest-first. Unknown/foreign/malformed id → `404 not-found` (catalog existence/uuid check before any detail query).

Same 404 semantics.

    - `GET /api/v1/tenants/{tenantId}/warehouses/{warehouseId}/inventory/events?skuId&cursor&limit` → `200` `{items: [{id, seq, type, skuId, fromBinId, toBinId, quantityDelta, actorUserId, occurredAt, recordedAt, eventHash, createdAt}], nextCursor}` — the event timeline read (newest first, keyset cursor pagination, limit 1–200; `400 invalid-cursor` on crafted cursors). - OpenAPI document (the contract): served at `GET /api/v1/openapi.json`; exported to `openapi/openapi.json` via `bun run openapi:export`. The frontend generates its typed client from this file — after any backend contract change run `bun run openapi:export` here, then `bun run api:generate` in wms-fe, and commit the regenerated client. The `Idempotency-Key` header is pinned in the spec (26-char Crockford base32 ULID pattern) and response ids carry `format: uuid` with uuid-v7 examples.
- Shared types/DTOs (source of truth, how the frontend consumes them): generated in wms-fe under `src/lib/api/generated/` via `@hey-api/openapi-ts` — no hand-written API types on the consuming side. Response DTOs live next to the controllers (`HealthResponse`, `EchoResponse`, tenancy DTOs in `src/modules/tenancy/tenancy.dto.ts`).
- **CORS (review-loop browser-testing fix):** browser clients are an **origin allow-list** — `CORS_ORIGIN` env (comma-separated, default `http://localhost:3001`, the web dev server), enabled via `enableCors` in `app.factory.ts`. No wildcard and no credentials (auth rides the `Authorization` header, so cookies are never needed); extend the list for deployed frontend origins.
- **Idempotency replay carve-out (epic-1 retro item 2):** role-gated commands re-evaluate authority **before** the replay lookup (deliberate fail-closed, story 1.5) — a same-key replay whose actor no longer holds the capability returns `403 role-denied` **naming the role and capability, not the snapshot**; the "replays re-serve the original response" promise above holds only while the actor's current role still authorizes the command. The FE is unaffected (fresh ULID per submit), but API clients that reuse keys on transport retries must expect the re-evaluated denial.
- Auth mechanism offered: 15-minute HS256 JWT from `POST /tenants/sign-in` (`JWT_SECRET` env, no refresh token yet — sign in again on expiry). Warehouse endpoints require it **and declare it in OpenAPI** (`addBearerAuth()` in `app.factory.ts` + `@ApiBearerAuth()` per endpoint → `security: [{"bearer": []}]` on the warehouse operations, so generated clients/Swagger UI know the scheme); `GET /health` and `POST /echo` stay anonymous.
- Breaking-change policy (deprecation window, versioning approach): the versioned document (`/api/v1` + doc `info.version`) is the contract; additive changes only while stories land in order — breaking changes to consumed shapes must be coordinated through the wms-fe contract update first (backend lands before the frontend that consumes it).
