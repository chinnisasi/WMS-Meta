- Local path: `workspace/core/backend/wms-be`

Durable notes about this repo (architecture, conventions, what it exposes to `wms-fe`) go here. Repo-local operational docs (setup, scripts, etc.) stay inside the repo itself.

## Stack & structure (Story 1.2)

- NestJS 12 modular monolith (TypeScript 6, bun as package manager), api shell (`src/api/`) + jobs shell (`src/jobs/`), 13 spine module folders under `src/modules/` per ARCHITECTURE-SPINE.md §Structural Seed: tenancy, catalog, inventory, inbound, putaway, outbound, movements, replenishment, channels, compliance, reporting, carriers, notifications. **Tenancy owns the first tables** (`tenants`, `users`, `warehouses`, `zones`, `bins`, `idempotency_keys` — all uuidv7 PKs with `tenant_id` stamped on every row); **catalog is the second real module** (story 1.4: `skus`, `uom_conversions`, `catalog_imports`, `catalog_import_errors`); other spine modules are still stubs.
- Modules own their tables exclusively and talk via interfaces/domain events — the tenancy command services (registration, sign-in, warehouse create) are the command-layer precedent: validate → hash → write → emit domain event through the seam (`LoggingEventBus`, `EVENT_BUS` token).
- Shared primitives in `src/shared/`: UUIDv7 ids, ULID idempotency keys, ISO-8601 UTC timestamps, integer paise, base-UoM integer quantities, GST basis points, cursor pagination, RFC 9457 problem-details (machine-readable `code`), idempotency/event-bus/outbox seams. The `Database` DI provider (`DATABASE` token in SharedModule) is a lazy proxy — boot never requires `DATABASE_URL`; the first query connects.
- **Two database connections (review loop 1 decision):** besides the scoped `DATABASE` connection there is an `AUTH_DATABASE` connection (`createLazyAuthDatabase`, `DATABASE_AUTH_URL` env, falling back to `DATABASE_URL`). It exists because the fail-closed RLS policies hide **all** rows from a non-superuser role with no `app.tenant_id` set — which sign-in and the registration replay lookup need (they run *before* any tenant context exists). The `DATABASE_AUTH_URL` role **must carry `BYPASSRLS`** (no tenant scope is safe or intended at auth time); `AUTH_DATABASE` is used **only for reads** by `sign-in.command.ts` and the replay lookup in `registration.command.ts` — never for writes (writes always go through the scoped `DATABASE` transaction with `setTenantScope`). In dev/CI it falls back to the superuser `wms` user (a boot-time warning fires on fallback). **Role provisioning:** `scripts/provision-roles.sql` creates the mandated pair — non-superuser `wms_app` for `DATABASE_URL`, non-superuser `BYPASSRLS` `wms_auth` for `DATABASE_AUTH_URL` (BYPASSRLS bypasses policies but not grants, so it also gets table grants). The e2e suite provisions its own `wms_auth_probe` role and points `DATABASE_AUTH_URL` at it, so sign-in/replay are exercised under RLS-binding conditions, not the superuser fallback.
- **Drizzle + RLS gap:** drizzle-orm 0.45.2 cannot model RLS in the schema (no `enableRLS`; `pgPolicy` would emit conflicting `CREATE POLICY` against the hand-written DDL), so the drizzle snapshot says `isRLSEnabled: false`. RLS DDL lives **only** in migration SQL — never rely on drizzle-kit for RLS; carry the DDL in migrations by hand.
- Drizzle (0.45.2) migrations on Postgres (`drizzle/`, runner `bun run db:migrate`, needs `DATABASE_URL`; dev DB via the repo's `docker-compose.yml` — postgres:18-alpine on host port 55432, user/password/db `wms`).
- **Multi-tenancy mechanism:** every table carries `tenant_id`; the app sets it per transaction via `select set_config('app.tenant_id', $1, true)` (see `src/shared/db/tenant-scope.ts` — moved there in story 1.4 so every module shares the `TenantTx` helper) and Postgres RLS is enabled with `USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)` policies on all tenant-bearing tables (migration `0001_greedy_scarecrow.sql` for the tenancy set — tenants, users, warehouses, idempotency_keys — and `0003_good_ulik.sql` / `0004_previous_otto_octavius.sql` for the later zone/bin and catalog tables). **The empty-string NULLIF is load-bearing** — PG 18's `current_setting(..., true)` returns `''` (not NULL) after a transaction-local value expires, and a bare `''::uuid` cast throws. **Caveat: RLS is defense-in-depth only for non-superuser roles** — the docker-compose `wms` user is a superuser and bypasses RLS even with FORCE; the deployed app role must be a non-superuser (verified by the `wms_rls_probe` e2e test).
- **Idempotency:** real storage landed in the tenancy module (`idempotency_keys`: unique `(tenant_id, key)`, payload hash, response snapshot). Replays are de-duped **in the same transaction** as the write; same key + same payload replays the original response, same key + different payload → `422 idempotency-key-reuse`. The payload-hash fingerprint covers **`{name, ownerEmail}` only — never password material**: the raw password would make a leaked idempotency row an offline password oracle, and the scrypt hash is salted (random per call), so it is not replay-deterministic. Registration (no tenant context yet) looks up by key alone on `AUTH_DATABASE` and stamps the new tenant id on the row; a foreign replay fails the hash comparison and 422s, so nothing leaks. Concurrent same-key requests are arbitrated by the unique index — the 409 `conflict` handler wraps the idempotency-row INSERT itself. **Indexing:** besides the unique `(tenant_id, key)` index there is a plain `idempotency_keys(key)` index (migration `0002_misty_romulus.sql`) — the registration replay's key-only lookup runs on a table that grows on every mutating request. Registration orders its work **fingerprint → replay lookup → scrypt hash** so a replay never pays the ~100 ms hashing cost.
- **Post-commit events:** domain events publish **after** the transaction commits, and the publish is guarded — a throwing bus logs a warning and the command still returns its 2xx (the client's retry would replay instead of re-emit). `LoggingEventBus` logs `type`, `tenantId`, and `eventId` only — **never payloads** (event bodies can carry PII like owner emails).
- **Sessions:** 15-minute HS256 JWTs hand-signed with `node:crypto` (`src/modules/tenancy/jwt-session.ts`; claims `sub` + `tenant_id`, `exp` ≤ 900 s) — no refresh tokens. The signing secret is `JWT_SECRET` (≥ 16 chars, required at sign-in/verification time). Passwords are scrypt hashes via `node:crypto`.
- **Zero-warehouse invariant:** `TenancyService.requireActiveWarehouse(tenantId)` throws `422 no-active-warehouse` — Epic 2 consumes this before any stock write.
- **Warehouse-scoped master data (Story 1.3):** `zones` and `bins` are the first tables to carry `warehouse_id` alongside `tenant_id`. **Warehouse ownership is app-layer** — `assertWarehouseInTenant(tx, tenantId, warehouseId)` (in `tenancy.service.ts`) runs inside the command transaction before any zone/bin write and answers foreign/nonexistent warehouses with `404 not-found`; **RLS stays single-dimension** (`<table>_tenant_isolation` on `tenant_id` only, hand-written DDL in migration `0003_good_ulik.sql`) — composite (tenant + warehouse) policies are rejected. No FK constraints: `bins.zone_id` → `zones.id` → `warehouses.id` are uuid columns + indexes validated in the command transactions. Bin codes are unique per warehouse (`bins_warehouse_id_code_unique` — not per zone); zone codes per warehouse (`zones_warehouse_id_code_unique`); duplicate rejections name the conflicting code. Bin `type` is the fixed set `shelf|pallet|floor|staging`, `capacity` a positive integer in base-UoM units, `blocked` (default false) marks broken bins; **no bin/zone editing beyond `blocked`** in this story.
- **Grid generator (Story 1.3):** `BinCommand.generateGrid` mass-creates bins from an aisle-letter range (A–Z ascending) × bays × levels, zero-padded `A-01-01` codes, **capped at 500 bins per run** (`422 grid-too-large` above). One `withTenantTransaction`, one idempotency record — all-or-nothing; a collision pre-check in the same transaction fails the run naming the first conflicting code with nothing committed (`409 duplicate-bin-code`), and a same-key replay re-serves the stored snapshot.
- **Setup checklist (Story 1.3, catalog step wired in 1.4):** `GET /tenants/{tenantId}/setup-checklist` is **computed on read** — no stored step rows. Steps: `warehouse` (done at ≥1 warehouse), `bins` (done at ≥1 bin), `catalog` (story 1.4 — done at ≥1 SKU; `CatalogModule` is imported by `TenancyModule` and the step aggregates through `CatalogFacade.getImportSummary`, the first cross-module facade consumption: detail reads `Done · N SKUs · last import X committed, Y failed`, and stays honest when a tenant has import history but zero committed SKUs), `users` (wired in story 1.5 — done at ≥1 invited team member, see the Story 1.5 bullet below). Each step carries `key`, `label`, `done`, `detail`, `href` (deep link, `/settings` today).
- **Catalog module (Story 1.4):** owns `skus` (unique `(tenant_id, code)` and `(tenant_id, barcode)` per tenant), `uom_conversions` (unique `(sku_id, uom)`, positive-integer factors relative to the base UoM), `catalog_imports` (run ledger), `catalog_import_errors` (row-level rejections) — migration `0004_previous_otto_octavius.sql` with hand-written fail-closed RLS on all four (same `tenant_isolation` pattern, no FKs). **The import is synchronous multipart CSV/XLSX** (≤ 10,000 data rows, ≤ 5 MB): valid rows commit in **one transaction** and bad rows are returned per row `{rowNumber, skuCode, code, detail}` — partial commit is honest, a `201` can carry failures. Duplicate SKU codes / barcode collisions are **row-level** rejections naming the conflict (`duplicate-sku-code` / `duplicate-barcode`) when the conflicting row is already committed before the run starts. A `409` can still fail a **whole import** in two transient races: a concurrent import introducing the same SKU code / barcode (the pre-check passes, the row insert hits the unique index — retry re-runs the row-level checks), and concurrent imports sharing one Idempotency-Key (the loser's idempotency-row INSERT hits the unique index → `409 conflict`, same arbitration as registration). Fix mode (`mode=fix`) is **set-membership against the latest run**: only rows whose SKU code appears in that run's `catalog_import_errors` are processed; everything else counts `skippedRows` and is untouched — a clean fix run leaves an empty set, so the next fix round skips everything. There is **no manual SKU create** — catalog entries enter only through import, then are edited via PATCH (the SKU code is immutable). Barcodes are generated server-side (uuidv7) unless the file provides one. The import payload fingerprint is **sha256(file bytes) + mode** — a replay re-serves counts + error list; a different file on the same key is `422 idempotency-key-reuse`. File-level failures: `415 unsupported-file-type` (not .csv/.xlsx), `400 file-unreadable` (garbage bytes, unknown/missing header columns, header with no data rows), `422 import-too-large` (row cap, byte cap — multer's `LIMIT_FILE_SIZE` arrives as a 413 `PayloadTooLargeException` and the route-scoped `CatalogUploadFilter` translates it to `422 import-too-large` problem-details). GST is stored as **basis points** (0–10000); row validation order: shape → gst range → uom factor → duplicates. **The `EVENT_BUS` provider moved from TenancyModule to SharedModule** (`src/shared/events/event-bus.ts`) in this story — catalog is the first cross-module event emitter (`catalog.imported`, `catalog.sku_edited`), same post-commit guarded publish.
- **Users, roles, permission gating (Story 1.5):** the `users` table gains `role` (`owner|ops_manager|operator|accountant`, default `owner` for the registering user) and `status` (`invited|active`). **Authorization is per-command, DB-read based** — `getMemberRoleIn`/`getMemberRole` read the caller's current role **inside the command transaction** (the JWT carries only `sub` + `tenant_id`; it is transport, never authority), so a role change is effective on the caller's next command without re-login. The capability matrix lives in `src/modules/tenancy/permissions.ts`: `owner` holds all 8 capabilities (`warehouse.create`, `zone.create`, `bin.create`, `bin.block`, `catalog.import`, `sku.edit`, `users.invite`, `users.role_change`), `ops_manager` the six operational ones (no users.*), `operator`/`accountant` none — **reads are never gated**. Denials are `403 role-denied` naming the role and the missing capability. **Invites:** `POST /tenants/{tenantId}/users` `{email, role}` creates the user `invited` with a `DUMMY_HASH` password and returns `inviteToken` (raw base64url — its only durable stores are this response and the idempotency snapshot; only its sha256 hash lives on the users row) + 7-day `inviteExpiresAt`; there is no email delivery — the owner shares the one-time link out-of-band. A same-Idempotency-Key replay re-serves the original response (same token); a **fresh key** against an email that already belongs to any user of any tenant — `invited` or active, the pre-check has no status filter — is `409 email-exists`. **`POST /tenants/{tenantId}/accept-invite` is unauthenticated** `{token, password}` → sets the scrypt hash, flips status to `active`, returns the user; the token is valid only on the inviting tenant's URL, and unknown/expired/burned tokens are one indistinguishable `400 invite-invalid` (one-time use, 7-day TTL — the accept UPDATE is itself conditional on the invite still being pending, so concurrent accepts cannot double-fire). An `invited` user attempting sign-in gets `403 invite-pending` for **any** password (the check runs before password verification, burning one scrypt round so timing does not leak account state). **Role changes:** `PATCH /tenants/{tenantId}/users/{userId}` `{role}`; demoting the **last owner** → `409 last-owner` with nothing persisted (a second owner unlocks it); every invite, role change, and accept writes an `audit_events` row (actor, action, target, reference). **`GET /tenants/{tenantId}/me`** returns the caller's own row (`{user}`) — the frontend bootstraps it on app mount so role changes surface without re-login. Sign-in's response now carries `user {id, email, role, status}` alongside the tenant. **RLS deepening:** `audit_events` (migration `0005_colorful_dreaming_celestial.sql`, same `tenant_isolation` pattern) and the users columns are covered by the fail-closed RLS policies; the e2e suite probes them with non-superuser roles (`wms_rls_probe` / `wms_auth_probe` — probe-role DDL is serialized across jest workers with `pg_advisory_xact_lock` to dodge Postgres `tuple concurrently updated` races). The setup checklist's `users` step is now wired (story 1.5): done at ≥1 invited team member, detail `Done · N team member(s) invited`.

## Interface Contract (what this repo provides to `wms-fe`)

Keep this current whenever a cross-repo change lands — this is what lets an agent catch "this backend change breaks the frontend" *before* making the change, not after.

- API base path / version exposed: `/api/v1` (document version 1.0.0)
- Endpoints offered (Story 1.1 + 1.2 + 1.3 + 1.4 + 1.5 scope): `GET /api/v1/health`, `POST /api/v1/echo`, `GET /api/v1/openapi.json` (Swagger UI at `/api/docs`); plus the tenancy surface —
  - `POST /api/v1/tenants` `{name, ownerEmail, password}` → `201` tenant + owner user (no password material exposed). Requires an `Idempotency-Key` header (missing/malformed → `400`; key reuse with a different payload → `422 idempotency-key-reuse`). Owner-email uniqueness is **global** (one tenant per email); duplicate → `409 duplicate-email`. String inputs are **trimmed at the validation boundary** (`@Transform` in `tenancy.dto.ts`) — a padded `" a@b.com "` validates like its trimmed form, and whitespace-only fields fail `@Length`.
  - `POST /api/v1/tenants/sign-in` `{email, password}` → `200` `{accessToken, tokenType: 'Bearer', expiresInSeconds: 900, tenant, user: {id, email, role, status}}` (story 1.5 added `user`). Unknown email vs wrong password are indistinguishable → `401 unauthenticated`; an `invited` user gets `403 invite-pending` for any password.
  - `POST /api/v1/tenants/{tenantId}/warehouses` `{code, name}` → `201` warehouse; requires the sign-in JWT (`Authorization: Bearer`) **and** the path tenantId must match the token's `tenant_id` (mismatch → `403 permission-denied`); requires `Idempotency-Key`; duplicate code → `409 duplicate-warehouse-code` naming the code.
  - `GET /api/v1/tenants/{tenantId}/warehouses?cursor&limit` → `200` `{items, nextCursor}` (keyset pagination, same auth + tenant-ownership rules; `limit` is validated 1–200 → `400 validation-failed` outside the range).
  - Zones/bins surface (Story 1.3 — all require the sign-in JWT, the path `tenantId` must match the token's `tenant_id`, and all mutating routes require `Idempotency-Key`):
    - `POST /api/v1/tenants/{tenantId}/warehouses/{warehouseId}/zones` `{code, name}` → `201` zone. Foreign/nonexistent warehouse → `404 not-found`; duplicate code → `409 duplicate-zone-code` naming the code.
    - `GET .../zones?cursor&limit` → `200` `{items, nextCursor}` (keyset, limit 1–200, `400 invalid-cursor` on crafted cursors).
    - `GET .../zones/{zoneId}/bins?cursor&limit` → `200` `{items, nextCursor}` (keyset, limit 1–200, `400 invalid-cursor` on crafted cursors / `400 validation-failed` on out-of-range limit; foreign zone → `404 not-found`). Created bins are immediately listed — no dormant state.
    - `POST .../zones/{zoneId}/bins` `{code, capacity, type}` → `201` bin (immediately usable downstream — no dormant state). Duplicate code → `409 duplicate-bin-code` naming the code (unique per **warehouse**, across zones); foreign zone → `404 not-found`.
    - `POST .../zones/{zoneId}/bins/grid` `{aisleFrom, aisleTo, baysPerAisle, levelsPerBay, capacity, type}` → `201` `{warehouseId, zoneId, generatedCount, firstCode, lastCode}`; ≤ 500 bins (`422 grid-too-large`), one transaction + one idempotency record; any code collision → `409 duplicate-bin-code` naming the first conflicting code, **nothing committed**; same-key replay re-serves the same snapshot.
    - `PATCH /api/v1/tenants/{tenantId}/warehouses/{warehouseId}/bins/{binId}` `{blocked}` → `200` bin — the only bin edit in this story; unknown bin → `404 not-found`.
    - `GET /api/v1/tenants/{tenantId}/setup-checklist` → `200` `{steps: [{key, label, done, detail, href}]}`, computed on read (see above); session-guarded like the other tenancy reads.
  - Catalog surface (Story 1.4 — all require the sign-in JWT, the path `tenantId` must match the token's `tenant_id`; both mutating routes require `Idempotency-Key`):
    - `POST /api/v1/tenants/{tenantId}/catalog/imports` (multipart/form-data: binary `file`, optional `mode=initial|fix`) → `201` `{importId, mode, committedRows, failedRows, skippedRows, errors: [{rowNumber, skuCode, code, detail}]}` — **a 201 can carry failures** (partial commit, see the catalog bullet above). Row-level `code` values: `validation-failed`, `duplicate-sku-code`, `duplicate-barcode`. File-level errors: `400 file-unreadable`, `415 unsupported-file-type`, `422 import-too-large` / `idempotency-key-reuse`; missing file → `400 validation-failed`. Replay with the same key + file re-serves the exact snapshot; different file on the same key → `422 idempotency-key-reuse`. Documented header: `sku_code,name,uom,uom_conversions,gst_rate,hsn,batch_tracked,serial_tracked,reorder_point,reorder_qty,barcode` (first four required; `uom_conversions` entries look like `box:12;case:144`; `gst_rate` in basis points).
    - `GET /api/v1/tenants/{tenantId}/catalog/skus?cursor&limit` → `200` `{items: [{id, code, name, uom, gstRateBps, hsn, batchTracked, serialTracked, reorderPoint, reorderQty, barcode, uomConversions, createdAt}], nextCursor}` (keyset, limit 1–200, `400 invalid-cursor` on crafted cursors).
    - `PATCH /api/v1/tenants/{tenantId}/catalog/skus/{skuId}` (body fields all optional: `name, gstRate (basis points), hsn (string or null), batchTracked, serialTracked, reorderPoint, reorderQty, barcode`) → `200` SKU — the SKU `code` is not part of the contract (immutable; unknown fields rejected by the whitelist). Unknown SKU → `404 not-found`; barcode collision → `409 duplicate-barcode` naming the conflicting SKU's code; empty body → `400 validation-failed`. Same-key replay re-serves the snapshot; different payload → `422 idempotency-key-reuse`.
  - Users/roles surface (Story 1.5 — all require the sign-in JWT and the path `tenantId` matching the token's `tenant_id`, except accept-invite; **reads are open to every tenant member**, the two mutations are Owner-capability-gated `403 role-denied`; all mutating routes require `Idempotency-Key`):
    - `POST /api/v1/tenants/{tenantId}/users` `{email, role: 'operator'|'accountant'|'ops_manager'|'owner'}` → `201` `{user: {id, email, role, status: 'invited', createdAt}, inviteToken, inviteExpiresAt}` — the raw one-time token (sha256-hashed on the users row; the raw value also persists in the idempotency snapshot so a replay re-serves it), 7-day TTL; no email delivery, the owner shares the link out-of-band. A same-Idempotency-Key replay re-serves the original response; a fresh key against an email that already belongs to any user of any tenant (`invited` or active) → `409 email-exists`; non-owner caller → `403 role-denied` naming role + capability.
    - `GET /api/v1/tenants/{tenantId}/users?cursor&limit` → `200` `{items: [{id, email, role, status, createdAt}], nextCursor}` (keyset, limit 1–200) — open to every tenant member.
    - `PATCH /api/v1/tenants/{tenantId}/users/{userId}` `{role}` → `200` updated user — Owner capability `users.role_change`; demoting the last owner → `409 last-owner` (nothing persisted); unknown user → `404 not-found`. Effective on the target's **next command** (per-command DB role read) — no re-login.
    - `POST /api/v1/tenants/{tenantId}/accept-invite` **(unauthenticated)** `{token, password}` → `200` `{user}` (status flips `invited` → `active`, scrypt hash set); the token is valid only on the **inviting** tenant's URL, and unknown/expired/already-used tokens → `400 invite-invalid`.
    - `GET /api/v1/tenants/{tenantId}/me` → `200` `{user: {id, email, role, status, createdAt}}` — the caller's own row; the frontend bootstraps this on app mount so role changes surface without re-login.
  - All error responses are RFC 9457 problem+json with machine-readable `code` and `instance`. Story 1.5 adds the codes `role-denied` (403), `email-exists` (409), `last-owner` (409), `invite-invalid` (400), and `invite-pending` (403).
- OpenAPI document (the contract): served at `GET /api/v1/openapi.json`; exported to `openapi/openapi.json` via `bun run openapi:export`. The frontend generates its typed client from this file — after any backend contract change run `bun run openapi:export` here, then `bun run api:generate` in wms-fe, and commit the regenerated client. The `Idempotency-Key` header is pinned in the spec (26-char Crockford base32 ULID pattern) and response ids carry `format: uuid` with uuid-v7 examples.
- Shared types/DTOs (source of truth, how the frontend consumes them): generated in wms-fe under `src/lib/api/generated/` via `@hey-api/openapi-ts` — no hand-written API types on the consuming side. Response DTOs live next to the controllers (`HealthResponse`, `EchoResponse`, tenancy DTOs in `src/modules/tenancy/tenancy.dto.ts`).
- Auth mechanism offered: 15-minute HS256 JWT from `POST /tenants/sign-in` (`JWT_SECRET` env, no refresh token yet — sign in again on expiry). Warehouse endpoints require it **and declare it in OpenAPI** (`addBearerAuth()` in `app.factory.ts` + `@ApiBearerAuth()` per endpoint → `security: [{"bearer": []}]` on the warehouse operations, so generated clients/Swagger UI know the scheme); `GET /health` and `POST /echo` stay anonymous.
- Breaking-change policy (deprecation window, versioning approach): the versioned document (`/api/v1` + doc `info.version`) is the contract; additive changes only while stories land in order — breaking changes to consumed shapes must be coordinated through the wms-fe contract update first (backend lands before the frontend that consumes it).
