## Stack & structure (Story 1.2)

- NestJS 12 modular monolith (TypeScript 6, bun as package manager), api shell (`src/api/`) + jobs shell (`src/jobs/`), 13 spine module folders under `src/modules/` per ARCHITECTURE-SPINE.md §Structural Seed: tenancy, catalog, inventory, inbound, putaway, outbound, movements, replenishment, channels, compliance, reporting, carriers, notifications. **Tenancy owns the first tables** (`tenants`, `users`, `warehouses`, `zones`, `bins`, `idempotency_keys` — all uuidv7 PKs with `tenant_id` stamped on every row); **catalog is the second real module** (story 1.4: `skus`, `uom_conversions`, `catalog_imports`, `catalog_import_errors`); other spine modules are still stubs.
- Modules own their tables exclusively and talk via interfaces/domain events — the tenancy command services (registration, sign-in, warehouse create) are the command-layer precedent: validate → hash → write → emit domain event through the seam (`LoggingEventBus`, `EVENT_BUS` token).
- Shared primitives in `src/shared/`: UUIDv7 ids, ULID idempotency keys, ISO-8601 UTC timestamps, integer paise, base-UoM integer quantities, GST basis points, cursor pagination, RFC 9457 problem-details (machine-readable `code`), idempotency/event-bus/outbox seams. The `Database` DI provider (`DATABASE` token in SharedModule) is a lazy proxy — boot never requires `DATABASE_URL`; the first query connects.
- **Two database connections (review loop 1 decision):** besides the scoped `DATABASE` connection there is an `AUTH_DATABASE` connection (`createLazyAuthDatabase`, `DATABASE_AUTH_URL` env, falling back to `DATABASE_URL`). It exists because the fail-closed RLS policies hide **all** rows from a non-superuser role with no `app.tenant_id` set — which sign-in and the registration replay lookup need (they run *before* any tenant context exists). The `DATABASE_AUTH_URL` role **must carry `BYPASSRLS`** (no tenant scope is safe or intended at auth time); `AUTH_DATABASE` is used **only for reads** by `sign-in.command.ts`, the replay lookup in `registration.command.ts`, and the outbox relay's tenant-discovery query (`src/shared/events/outbox.ts`, story outbox-relay) — never for writes (writes always go through the scoped `DATABASE` transaction with `setTenantScope`). In dev/CI it falls back to the superuser `wms` user (a boot-time warning fires on fallback). **Role provisioning:** `scripts/provision-roles.sql` creates the mandated pair — non-superuser `wms_app` for `DATABASE_URL`, non-superuser `BYPASSRLS` `wms_auth` for `DATABASE_AUTH_URL` (BYPASSRLS bypasses policies but not grants, so it also gets table grants). The e2e suite provisions its own `wms_auth_probe` role and points `DATABASE_AUTH_URL` at it, so sign-in/replay are exercised under RLS-binding conditions, not the superuser fallback.
- **Drizzle + RLS gap:** drizzle-orm 0.45.2 cannot model RLS in the schema (no `enableRLS`; `pgPolicy` would emit conflicting `CREATE POLICY` against the hand-written DDL), so the drizzle snapshot says `isRLSEnabled: false`. RLS DDL lives **only** in migration SQL — never rely on drizzle-kit for RLS; carry the DDL in migrations by hand.
- Drizzle (0.45.2) migrations on Postgres (`drizzle/`, runner `bun run db:migrate`, needs `DATABASE_URL`; dev DB via the repo's `docker-compose.yml` — postgres:18-alpine on host port 55432, user/password/db `wms`).
- **Multi-tenancy mechanism:** every table carries `tenant_id`; the app sets it per transaction via `select set_config('app.tenant_id', $1, true)` (see `src/shared/db/tenant-scope.ts` — moved there in story 1.4 so every module shares the `TenantTx` helper) and Postgres RLS is enabled with `USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)` policies on all tenant-bearing tables (migration `0001_greedy_scarecrow.sql` for the tenancy set — tenants, users, warehouses, idempotency_keys — and `0003_good_ulik.sql` / `0004_previous_otto_octavius.sql` / `0005_colorful_dreaming_celestial.sql` / `0006_*.sql` / `0007_pretty_silver_samurai.sql` for the later tables — audit/ledger/outbox included). **The empty-string NULLIF is load-bearing** — PG 18's `current_setting(..., true)` returns `''` (not NULL) after a transaction-local value expires, and a bare `''::uuid` cast throws. **Caveat: RLS is defense-in-depth only for non-superuser roles** — the docker-compose `wms` user is a superuser and bypasses RLS even with FORCE; the deployed app role must be a non-superuser (verified by the `wms_rls_probe` e2e test).
- **Idempotency:** real storage landed in the tenancy module (`idempotency_keys`: unique `(tenant_id, key)`, payload hash, response snapshot). Replays are de-duped **in the same transaction** as the write; same key + same payload replays the original response, same key + different payload → `422 idempotency-key-reuse`. The payload-hash fingerprint covers **`{name, ownerEmail}` only — never password material**: the raw password would make a leaked idempotency row an offline password oracle, and the scrypt hash is salted (random per call), so it is not replay-deterministic. Registration (no tenant context yet) looks up by key alone on `AUTH_DATABASE` and stamps the new tenant id on the row; a foreign replay fails the hash comparison and 422s, so nothing leaks. Concurrent same-key requests are arbitrated by the unique index — the 409 `conflict` handler wraps the idempotency-row INSERT itself. **Indexing:** besides the unique `(tenant_id, key)` index there is a plain `idempotency_keys(key)` index (migration `0002_misty_romulus.sql`) — the registration replay's key-only lookup runs on a table that grows on every mutating request. Registration orders its work **fingerprint → replay lookup → scrypt hash** so a replay never pays the ~100 ms hashing cost.
- **Transactional outbox (story outbox-relay, PR #9 — replaces the old post-commit publish):** every domain event is now an in-transaction append to `outbox_messages` (migration `0007`: uuidv7 id, `tenant_id`, `type`, jsonb `payload`, business-time `occurred_at`, `status pending|quarantined` enforced by a CHECK, `attempts`, `next_attempt_at`, `last_error`; fail-closed `tenant_isolation` RLS hand-appended) — the event commits or rolls back **with** the write that produced it (AD-7). Suppression is structural: commands reach `append` only on the fresh-write path, so an idempotent replay writes **no** second row (this closes epic-1 retro item 3 — `users.command.ts` previously re-published on replay). `PostgresOutboxSink.append(tx, message)` is the write side (`OUTBOX_SINK` token); `PostgresOutboxRelay.drain(limit)` the read side. **Relay mechanics:** one `drain` call = one cycle — session-level advisory lock (`wms:outbox-relay`) serializes relay instances (a concurrent cycle sheds → `[]`, AD-17), tenant discovery reads due tenants oldest-first on `AUTH_DATABASE` (the sanctioned second cross-tenant read, read-only), each tenant drains in `(created_at, id)` order inside its own `withTenantTransaction`, publishes through the existing `EVENT_BUS` seam (`LoggingEventBus` unchanged — logs type/tenant/eventId, never payloads; the outbox row id **is** the relayed `eventId`), and deletes the row on ack — **at-least-once** (a crash between publish and ack re-publishes; consumers own exactly-once effect, AD-5). Failures retry with backoff `min(2^(attempts-1)·5s, 5min)`, quarantine after 5 attempts (DLQ), and rows skip instead of aborting the cycle (per-tenant/per-row fault isolation). **Delivered rows are deleted** (delete-on-ack — events derive from committed state). **Worker:** `OutboxRelayWorker` in `src/jobs/` polls `drain(100)` — env-gated OFF unless `OUTBOX_RELAY_POLL_MS` (positive-integer ms, e.g. `2000`; `0`/unset = off; a non-integer fails the boot loudly) is set — **every deployment that wants delivery must set it** (`.env.example` carries `2000`). **Operator DLQ replay:** quarantined rows re-drain only via `OUTBOX_OPERATOR_REPLAY_SQL` (exported in `src/shared/events/outbox.ts`): `UPDATE outbox_messages SET status='pending', attempts=0, next_attempt_at=now() WHERE id=$1 AND status='quarantined'`. **Event coverage:** all 11 event types across the 9 emitting files ride the outbox (tenancy: `tenant.registered`, `user.invited/role_changed/accepted`, `warehouse.created`, `zone.created`, `bins.generated`, `bin.blocked`; catalog: `catalog.imported`, `catalog.sku_edited`; inventory: `stock.adjusted`, `ledger.chain_broken` — the severity-1 alert now appends in its own small tenant transaction and a failed append **rejects `verifyChain`** instead of being swallowed). `test/outbox.spec.ts` observes rows + delivery (first event-observation tests in the repo); `test/outbox-worker.spec.ts` pins the worker.
- **Continuous replay-reconciliation (Story 2.2, PR #10):** a sheddable `ReconciliationWorker` (`src/jobs/jobs.module.ts`, mirror of the relay worker — env gate `OUTBOX_RECONCILE_POLL_MS` with the same conventions, in-process shed, `unref`'d timer, shutdown hook) drives per-(tenant, warehouse) cycles through `InventoryFacade.reconcileNext()`: **one partition per tick, oldest-checkpoint-first** (discovery reads `ledger_events` heads vs `reconciliation_checkpoints` on `AUTH_DATABASE` — the sanctioned third cross-tenant read, read-only). Each cycle: detection in **one repeatable-read tenant transaction** (checkpoint validation `last_seq ≤ head` — invalid twice in a row → discard + `reconciliation.checkpoint_invalid` outbox alert + full replay; a clean pass advances the checkpoint in the same snapshot; the compare window is bounded to the (sku, bin) scopes touched by events in `(last_seq, watermark]`, so a movement committing mid-cycle is the next cycle's problem, never a false positive), then — on divergence — a **repair transaction under the append path's per-warehouse advisory lock** (`rebuildProjectionsInTx` re-folds fresh so concurrently-committed movements are included, not clobbered) that also quarantines repeats and appends the `reconciliation.divergence` alert in the SAME commit (rebuild + alert always travel together; first divergence = rebuild + alert, a repeated divergence within the window = quarantine + re-alert; quarantine is a durable `inventory_quarantines` row — one open row per scope via a partial unique index — that Story 2.3's reservation path will consume). **New tables (migration `0008_lowly_khan.sql`, hand-appended fail-closed RLS + CHECKs, same 0007 pattern):** `reconciliation_checkpoints` (unique `(tenant, warehouse)`; `last_seq`, `invalid_attempts`, plus `last_divergences` jsonb — the story spec listed only the first two; the third is the implementation's repeat-detection memory: scopes flagged by the previous non-advanced pass) and `inventory_quarantines` (`status` CHECK `open|resolved`, `from_seq ≤ to_seq` CHECK). **Verify-before-anchor:** `anchorChain` runs `verifyChainInTx` over its range inside the anchor transaction and commits nothing over a broken range (returns the `ChainBreakReport`; the severity-1 `ledger.chain_broken` alert path is unchanged). `LedgerService.rebuildProjections` is the derived-state repair entry (the architecture test still pins stock_on_hand writes to `ledger.service.ts` alone); `InventoryFacade.reconcile/reconcileNext/rebuildProjections` are background/operator surfaces — **no new HTTP route, no OpenAPI change**. `test/reconciliation.spec.ts` covers the I/O matrix end to end.
- **Batch & serial traceability (Story 2.4, PR #13):** catalog gains batch/serial **identity** — `batches` (unique `(tenant, sku, code)`, mfg/expiry dates) and `serials` (unique `(tenant, sku, serial_number)`) tables, ensured idempotently through `CatalogFacade.ensureBatches`/`ensureSerials` (migration `0010_sharp_hardball.sql`, drizzle base + hand-appended fail-closed RLS + CHECKs + traceability indexes on `ledger_events(tenant_id, serial_ref, seq)` / `(tenant_id, batch_ref, seq)`). The ledger opens the reserved batch/serial arms on `stock.adjusted`: inventory gains the `batch_on_hand` projection (unique `(tenant, warehouse, sku, bin, batch)`) folded in the **same transaction** as append — and by replay / reconcile-scan / rebuild (the architecture test's single-projection-path pin now covers it); serial location is derived from the serial's latest ledger event; duplicate-scan/wrong-bin draws fail at ledger-write time (`409 duplicate-serial` naming the location). Serial-tracked movements are **one ledger event per serial unit** (N qty ±1 events, one idempotency record). Concurrency: per-serial tenant-wide advisory locks (keyed `tenant:serial:ref`) acquired in sorted order before the warehouse lock — no lock-order inversion. FEFO (CHECKPOINT 1): the api layer composes batch identity + FEFO resolution (catalog expiry × inventory batch-on-hand join, oldest non-expired with stock in the bin, expiry ASC nulls-last); the composition never sees a retry — **replay beats composition** (the command-owned fingerprint pre-check returns the stored snapshot even when the FEFO batch has since been exhausted); arms are normalized (null = absent, serials trimmed, empty array absent) before identity AND fingerprint; `stock.adjust` is asserted before any validation 400 or identity creation. Blocked/QC lifecycle (`status` columns) ships schema-only until Epic 3/4.

- **QC hold & release (Story 3.4, PR #18):** Ops Managers quarantine a (sku, bin) scope with **real ledger movements** — a hold appends one `qc.held` event per on-hand arm into the warehouse's **system QC-hold bin** (code `QC-HOLD`, type staging, system-owned, ensured lazily per warehouse by `ensureQcHoldBinInTx`; the QC bin itself can never be a hold origin → `400`), a release derives its arms by **replaying the hold's own `qc.held` ledger events** (`qcHeldArmsInTx` — same batch refs, same magnitudes) and appends `qc.released` back to the recorded origin bin (origin bin gone → `409 qc-hold-origin-bin-gone`, hold stays open). Release restores ATP automatically (the units simply leave the QC bin). No partial release, no scrap disposition (Epic 4+); mobile untouched; `qc.held`/`qc.released` register sinceVersion 1 — no grammar bump. Two boundary guards keep the QC bin hold/release-exclusive: a **serial-tracked SKU cannot be held bulk** (a bulk hold would strand its serial location records at the origin bin — `400`), and **stock adjustments cannot touch the QC bin** (`400 qc-bin-not-adjustable` — only the hold/release commands ever move stock through it). `test/qc-holds.spec.ts` covers the I/O matrix incl. ATP snapshot pins, replay, the warehouse-scoped holds list (filter + foreign-warehouse 404 + cursor walk), RLS, and the migration backstops.

- **Bin administration (Story 3.6):** the bin lifecycle completes — **block/unblock re-homes to the `putaway` module** (`BinStateCommand.setBlocked` in `src/modules/putaway/bin-state.command.ts`; the controller URL `PATCH .../bins/{binId}` and payload are unchanged, but the command now owns the `bin.blocked` outbox event and gains a system-bin guard — blocking a system bin → `400 validation-failed` naming the bin — plus a retired-bin 409 and an audit row; guards run on a `.for('update')` row read BEFORE the UPDATE). **Migration `0016_*.sql`:** `bins.retired_at`/`bins.retired_by` (timestamptz/uuid, one-way — retirement is terminal) + the pairing CHECK (both set together or neither, the 0014 release-pairing pattern). **New capability `bin.retire`** (Owner + Ops Manager; added to the FE/permissions mirror). **Merge** (`BinCommand.mergeBin`) moves a source bin's entire on-hand to a target through **real per-arm ledger events** (`bin.merged` — plain/batch/per-serial arms exactly like the movement commands, reference doc `{kind: 'bin-merge', mergeId}`; both bin rows locked `.for('update')` id-sorted, per-serial pre-locks sorted), gated all-or-nothing: the target's post-merge occupancy is computed BEFORE any append and an overflow refuses the whole merge (`400 bin-full` naming the target). - **Orders — manual entry, idempotent ingestion, acceptance reservation (Story 4.1):** the `outbound` module stops being a placeholder and ships the order aggregate, the first consumer of Epic 2's reservation machinery. **New tables (migration `0017_*.sql`, drizzle base + hand-appended fail-closed RLS + CHECKs, the 0016 pattern):** `orders` (`status` CHECK `accepted|cancelled` — the picking/packed/dispatched arms arrive with 4.3/4.5/4.6; `source` CHECK `manual|ingested`; `source_payload_hash`) and `order_lines` (`status` CHECK `open|backordered`, `qty > 0`, `reserved_qty >= 0`, `reserved_qty <= qty`). **One create path** serves manual entry and adapter-ready ingestion: per line it reserves `min(qty, ATP)` through `InventoryFacade.grantReservation` (`owner_type: 'order'`, 7-day TTL), and the unreserved remainder marks the line `backordered` with the shortfall derived at every read (the **fixed v1 backorder policy** — per-channel policy arrives with Epic 7). A line that keeps losing stock races backorders after bounded re-probes; it never fails the order. **Any grant failure releases every hold already taken and writes nothing** (`503 reservation-store-unavailable` fails the whole creation closed). **Channel dedup is a database-level partial unique index** on `(tenant, integration_id, external_event_id)`: the same payload redelivered returns the first order's snapshot with no new reservation, a *divergent* payload on the same ref is `422 order-source-conflict` naming the existing order. Channel adapters, webhook ingestion and signature verification are **not** here — Epic 7 plugs into this machinery as-is; `integration_id` is validated only as a uuid (no integrations table until then). **Cancel is flip-first:** the conditional `accepted → cancelled` UPDATE, the line reset (`reserved_qty`/`reservation_id` cleared so no roll-up reports a hold the order no longer owns — the journal keeps the trail via `owner_id`), the `order.cancelled` outbox event, the audit row and the idempotency key all commit together, and the releases follow. A crash between them leaves the order `cancelled` with live holds — ATP understated until the reaper, never stock freed under an order that still reads `accepted`. A hold a consuming flow has already **committed** refuses the cancellation up front (`409`); one committed inside the pre-check → release window is logged as an operational anomaly (the cancellation is durable by then). **New capability `orders.manage`** (Owner + Ops Manager; Operator/Accountant none — the FE/permissions mirror rides 4.2). - **Waves and picklists (Story 4.2):** the outbound module gains the wave aggregate — 4.1's accepted orders become the floor's work, and 4.3's mobile picking gets its task substrate. **New tables (migration `0018_*.sql`, drizzle base + hand-appended fail-closed RLS + CHECKs, the 0017 pattern):** `wave_policies` (`grouping` CHECK `single|batch`, `priority`, `max_orders`, `cutoff_local_time`, and a nullable **unvalidated** `carrier_ref` — the `orders.integration_id` precedent; there is no carriers table until 4.6), `waves` (CHECK `planned|released|cancelled` + terminal-instant pairing CHECKs), `picklists` (CHECK `planned|ready|cancelled`; `order_id` null on a batch picklist) and `picklist_lines` (CHECK `planned|cancelled` + a **slice-shape** CHECK — a line is either a real stop (`bin_id` set, `qty > 0`) or a real shortfall, never both and never neither). **Generation is operator-triggered** (`POST .../waves` with a policy and either an explicit order selection or a sweep), never a scheduled job. Quantities come from each order line's `reserved_qty`, never `qty` — a backordered line contributes only what acceptance actually held. **The walk is `bins.code` ascending:** bins carry no spatial data at all (no aisle/rack/level/sequence/coordinate column), and the grid generator's `A-01-01` convention sorts naturally, so code order *is* the walk for grid-generated warehouses and is stable-but-arbitrary otherwise — "steps" therefore means **distinct bin stops**, which is what makes the epic's `batch stops ≤ sum of single-order stops` inequality measurable (the e2e measures it by re-waving the same orders single). **A picklist's bin and batch are a SUGGESTION re-derived at pick time** (the putaway precedent), never an allocation: a reservation binds to `(tenant, warehouse, sku, owner)` with no bin, so a hard binding would invent a second reservation the inventory module knows nothing about — which is also why two open waves may legitimately suggest the same bin units. Within a bin, batches draw **FEFO against a per-bin budget** seeded from the plain projection (two batches of 10 in a bin holding 10 plan 10 units, not 20); stock the batch fold has not attributed draws with no batch suggestion, while units held by a blocked or expired batch stay undrawable (epic-2 retro a13, draw side). Unpickable bins are the putaway filter set — `blocked`, `system_owned` (so Receiving and QC-hold stock never plans) and retired. **One order belongs to at most one open wave**, enforced by a partial unique index on `picklist_lines (tenant, order_line_id, slice_seq) WHERE status <> 'cancelled'` *and* by `FOR UPDATE` on the selected order rows — the row lock is what makes the concurrent-generate race deterministic, the index is the backstop. **Release** flips the wave, drops a since-cancelled order's lines (flipped `cancelled`, not deleted), cancels a picklist left with nothing pickable, and is **refused `409 cutoff-passed`** once the policy cutoff has passed in **`Asia/Kolkata`** (a named constant — `warehouses` has no timezone column and the product is India-only); the clock comparison **fails closed**. Generation is never cutoff-gated — planning ahead of a cutoff is the point. **New capability `waves.manage`** (Owner + Ops Manager, covering policy writes). `test/waves.spec.ts` covers the matrix e2e (20 tests).
- **Real-time ATP & atomic reservations (Story 2.3, PR #12):** Valkey 9.1 (docker-compose on host port **56379**, `VALKEY_URL` env, `src/shared/valkey/` — `ValkeyClient` wraps two pre-declared-keys Lua scripts in `reservation-scripts.ts`: **grant** (ready-marker gate → counter-exists gate → nil guard → ceiling check → `INCRBY` + `EXPIRE`) and **release** (floored-at-0 `DECRBY` with `KEEPTTL`)) is the **atomic-decision store only — never the truth**. Keys are tenant-namespaced and hash-tagged: `wms:{tenantId}:wh:{warehouseId}:res:{skuId}` (+ `…:res:__ready__`), so a single warehouse's reservations live on one Redis cluster slot. Postgres gains the `reservations` journal (migration `0009_overjoyed_sway.sql`, hand-appended fail-closed RLS + CHECKs incl. positive-quantity and `state held|committed|released|expired`) as the durable truth, on the same 0008 pattern. **Model:** the Valkey counter holds *reserved* quantity (commit leaves the counter untouched — ATP loss transfers to the pick path in later epics); terminal transitions are conditional UPDATEs on the journal (one winner), then the release script floors the counter at 0. **Corruption recovery:** `rebuildReservationCounters` disarms (deletes `__ready__`) → seeds counters from a journal sum → disarms-corrects-arms again; grant Lua fails **closed** (`503`) while `__ready__` is missing or the counter is unreadable. A boot-time rebuild runs on `onModuleInit` (failure logs and keeps grants failing closed until a later rebuild succeeds). **Divergence detection = scheduled parity pass** (human decision at review loop 1): every reaper cycle compares each live scope's counter vs its journal sum (`held|committed`) on `BYPASSRLS` `AUTH_DATABASE` (the sanctioned fourth cross-tenant read, read-only) and rebuilds the warehouse on any mismatch; failures log and wait for the next cycle. **Expiry:** `ReservationService.expireDueReservations` (driven by a sheddable `ReservationReaper` in `src/jobs/`, env gate `RESERVATION_REAPER_POLL_MS` with the same conventions as the other workers — `.env.example` carries `2000`, and **every deployment must set it or holds never expire**) settles due holds in the journal, per-hold fault isolation, then runs the parity pass. **Facade surface (no HTTP):** `InventoryFacade`/`ReservationService` expose `grantReservation` (returns the held row; `409 unavailable` deterministic loser, `503` fail-closed on Valkey down — **renamed in story 4.1 to the machine code `reservation-store-unavailable`** (epic-2 retro A8). **This is the one NON-additive change of story 4.1** — the code was `unavailable` (503) before and is `unavailable` no longer, across **every reserving flow: ATP reads, grant, commit, release, and order accept/cancel**; `unavailable` now means the 409 race-loser and nothing else. A 503 means nothing was written and the call is retryable; a 409 means the decision was made and there is no stock. Every store-state arm answers the 503, including a counter the store cannot report. Verified at the time of the rename that **no consumer keyed on the old shape**: neither wms-fe nor wms-mobile has a `switch (error.code)` arm matching `unavailable` or any 503-family code (503s fall to a default arm rendering `detail` verbatim), and neither calls a reserving flow yet — an agent adding one must match the new code; same-quantity replay re-serves the held row, **different-quantity replay → 409 conflict** — human decision at review loop 1), `commitReservation`/`releaseReservation` (terminal, idempotent by state — released/expired rows answer 409/404-shaped deterministic errors), `atp` (= max(0, onHand-with-quarantine-excluded − reserved − qcHeld − buffer)), `rebuildReservationCounters`, `expireDueReservations`. Validation hardening: UUID-shaped tenant/warehouse/sku/reservation ids (400), positive-integer quantity, `ttlSeconds` ≤ ~10 years. **Story 2.3 adds NO HTTP surface and NO OpenAPI change** — the FE contract is unchanged; order wiring consumes these facade methods in Epic 4.
- **Sessions:** 15-minute HS256 JWTs hand-signed with `node:crypto` (`src/modules/tenancy/jwt-session.ts`; claims `sub` + `tenant_id`, `exp` ≤ 900 s) — no refresh tokens. - **Catalog module (Story 1.4):** owns `skus` (unique `(tenant_id, code)` and `(tenant_id, barcode)` per tenant), `uom_conversions` (unique `(sku_id, uom)`, positive-integer factors relative to the base UoM), `catalog_imports` (run ledger), `catalog_import_errors` (row-level rejections) — migration `0004_previous_otto_octavius.sql` with hand-written fail-closed RLS on all four (same `tenant_isolation` pattern, no FKs). **The import is synchronous multipart CSV/XLSX** (≤ 10,000 data rows, ≤ 5 MB): valid rows commit in **one transaction** and bad rows are returned per row `{rowNumber, skuCode, code, detail}` — partial commit is honest, a `201` can carry failures. Duplicate SKU codes / barcode collisions are **row-level** rejections naming the conflict (`duplicate-sku-code` / `duplicate-barcode`) when the conflicting row is already committed before the run starts. A `409` can still fail a **whole import** in two transient races: a concurrent import introducing the same SKU code / barcode (the pre-check passes, the row insert hits the unique index — retry re-runs the row-level checks), and concurrent imports sharing one Idempotency-Key (the loser's idempotency-row INSERT hits the unique index → `409 conflict`, same arbitration as registration). Fix mode (`mode=fix`) is **set-membership against the latest run**: only rows whose SKU code appears in that run's `catalog_import_errors` are processed; everything else counts `skippedRows` and is untouched — a clean fix run leaves an empty set, so the next fix round skips everything. There is **no manual SKU create** — catalog entries enter only through import, then are edited via PATCH (the SKU code is immutable). Barcodes are generated server-side (uuidv7) unless the file provides one. The import payload fingerprint is **sha256(file bytes) + mode** — a replay re-serves counts + error list; a different file on the same key is `422 idempotency-key-reuse`. File-level failures: `415 unsupported-file-type` (not .csv/.xlsx), `400 file-unreadable` (garbage bytes, unknown/missing header columns, header with no data rows), `422 import-too-large` (row cap, byte cap — multer's `LIMIT_FILE_SIZE` arrives as a 413 `PayloadTooLargeException` and the route-scoped `CatalogUploadFilter` translates it to `422 import-too-large` problem-details). GST is stored as **basis points** (0–10000); row validation order: shape → gst range → uom factor → duplicates. **The `EVENT_BUS` provider moved from TenancyModule to SharedModule** (`src/shared/events/event-bus.ts`) in this story — catalog is the first cross-module event emitter (`catalog.imported`, `catalog.sku_edited`), same post-commit guarded publish.
- **Users, roles, permission gating (Story 1.5):** the `users` table gains `role` (`owner|ops_manager|operator|accountant`, default `owner` for the registering user) and `status` (`invited|active`). **Authorization is per-command, DB-read based** — `getMemberRoleIn`/`getMemberRole` read the caller's current role **inside the command transaction** (the JWT carries only `sub` + `tenant_id`; it is transport, never authority), so a role change is effective on the caller's next command without re-login. The capability matrix lives in `src/modules/tenancy/permissions.ts`: `owner` holds all 8 capabilities (`warehouse.create`, `zone.create`, `bin.create`, `bin.block`, `catalog.import`, `sku.edit`, `users.invite`, `users.role_change`), `ops_manager` the six operational ones (no users.*), `operator`/`accountant` none — **reads are never gated**. Denials are `403 role-denied` naming the role and the missing capability. **Invites:** `POST /tenants/{tenantId}/users` `{email, role}` creates the user `invited` with a `DUMMY_HASH` password and returns `inviteToken` (raw base64url — its only durable stores are this response and the idempotency snapshot; only its sha256 hash lives on the users row) + 7-day `inviteExpiresAt`; there is no email delivery — the owner shares the one-time link out-of-band. A same-Idempotency-Key replay re-serves the original response (same token); a **fresh key** against an email that already belongs to any user of any tenant — `invited` or active, the pre-check has no status filter — is `409 email-exists`. **`POST /tenants/{tenantId}/accept-invite` is unauthenticated** `{token, password, tenantId}` (the tenantId is folded into the idempotency payload hash — a mismatched one is `invite-invalid`) → sets the scrypt hash, flips status to `active`, returns the user; the token is valid only on the inviting tenant's URL, and unknown/expired/burned tokens are one indistinguishable `400 invite-invalid` (one-time use, 7-day TTL — the accept UPDATE is itself conditional on the invite still being pending, so concurrent accepts cannot double-fire). An `invited` user attempting sign-in gets `403 invite-pending` for **any** password (the check runs before password verification, burning one scrypt round so timing does not leak account state). **Role changes:** `PATCH /tenants/{tenantId}/users/{userId}` `{role}`; demoting the **last owner** → `409 last-owner` with nothing persisted (a second owner unlocks it); every invite, role change, and accept writes an `audit_events` row (actor, action, target, reference). **`GET /tenants/{tenantId}/me`** returns the caller's own row (`{user}`) — the frontend bootstraps it on app mount so role changes surface without re-login. Sign-in's response now carries `user {id, email, role, status}` alongside the tenant. **RLS deepening:** `audit_events` (migration `0005_colorful_dreaming_celestial.sql`, same `tenant_isolation` pattern) and the users columns are covered by the fail-closed RLS policies; the e2e suite probes them with non-superuser roles (`wms_rls_probe` / `wms_auth_probe` — probe-role DDL is serialized across jest workers with `pg_advisory_xact_lock` to dodge Postgres `tuple concurrently updated` races). The setup checklist's `users` step is now wired (story 1.5): done at ≥1 invited team member, detail `Done · N team member(s) invited`.

## Interface Contract (what this repo provides to `wms-fe`)

Keep this current whenever a cross-repo change lands — this is what lets an agent catch "this backend change breaks the frontend" *before* making the change, not after.

- Endpoints offered (Story 1.1 + 1.2 + 1.3 + 1.4 + 1.5 scope): `GET /api/v1/health`, `POST /api/v1/echo`, `GET /api/v1/openapi.json` (Swagger UI at `/api/docs`); plus the tenancy surface —

- OpenAPI document (the contract): served at `GET /api/v1/openapi.json`; exported to `openapi/openapi.json` via `bun run openapi:export`. The frontend generates its typed client from this file — after any backend contract change run `bun run openapi:export` here, then `bun run api:generate` in wms-fe, and commit the regenerated client. The `Idempotency-Key` header is pinned in the spec (26-char Crockford base32 ULID pattern) and response ids carry `format: uuid` with uuid-v7 examples.
- Shared types/DTOs (source of truth, how the frontend consumes them): generated in wms-fe under `src/lib/api/generated/` via `@hey-api/openapi-ts` — no hand-written API types on the consuming side. Response DTOs live next to the controllers (`HealthResponse`, `EchoResponse`, tenancy DTOs in `src/modules/tenancy/tenancy.dto.ts`).
- **CORS (review-loop browser-testing fix):** browser clients are an **origin allow-list** — `CORS_ORIGIN` env (comma-separated, default `http://localhost:3001`, the web dev server), enabled via `enableCors` in `app.factory.ts`. No wildcard and no credentials (auth rides the `Authorization` header, so cookies are never needed); extend the list for deployed frontend origins.
- **Idempotency replay carve-out (epic-1 retro item 2):** role-gated commands re-evaluate authority **before** the replay lookup (deliberate fail-closed, story 1.5) — a same-key replay whose actor no longer holds the capability returns `403 role-denied` **naming the role and capability, not the snapshot**; the "replays re-serve the original response" promise above holds only while the actor's current role still authorizes the command. The FE is unaffected (fresh ULID per submit), but API clients that reuse keys on transport retries must expect the re-evaluated denial.
- Auth mechanism offered: 15-minute HS256 JWT from `POST /tenants/sign-in` (`JWT_SECRET` env, no refresh token yet — sign in again on expiry). Warehouse endpoints require it **and declare it in OpenAPI** (`addBearerAuth()` in `app.factory.ts` + `@ApiBearerAuth()` per endpoint → `security: [{"bearer": []}]` on the warehouse operations, so generated clients/Swagger UI know the scheme); `GET /health` and `POST /echo` stay anonymous.
- Breaking-change policy (deprecation window, versioning approach): the versioned document (`/api/v1` + doc `info.version`) is the contract; additive changes only while stories land in order — breaking changes to consumed shapes must be coordinated through the wms-fe contract update first (backend lands before the frontend that consumes it).
