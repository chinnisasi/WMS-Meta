## Findings

Provenance: **[AD]** architecture-delta analyst, **[DV]** duplication/pattern analyst, **[SR]** spec-reconciliation analyst, **[BE]** backend-boundary review lens, **[FE]** frontend/mobile review lens, **[SM]** behavior smoke. Findings F1–F12 triaged in Phase 4; observations O1–O4 recorded as decisions-to-confirm.

### High

- **F1 (FE, high) — Product edit form silently corrupts a product's axes.** The edit field prefills the *display* grammar (`productAxesLabel` → `"size · colour"`) but `parseProductAxes` splits on commas only, so saving an unattached product's edit — even a name-only change — PATCHes `axes: ["size · colour"]`: one axis literally named `"size · colour"`, which passes every backend check. No error; the variant label then renders `size · colour: M`. Only the **create** path is test-pinned; the edit round-trip is the verification gap. — [FE] `wms-fe/src/components/settings/products-card.tsx:508`, `src/lib/catalog-products.ts:25,40`; backend checks `product.command.ts` `assertAxes`.
- **F2 (BE, high) — Write-skew: concurrent kit create can strand stock on a kit SKU forever.** The +stock writers other than GRN — stock adjustment (`inventory.command.ts:592`) and over-receipt approval (`receiving.command.ts:895-907`) — never take the SKU row lock the kit-create guards serialize on (`.for('update')`, given only to GRN at `receiving.command.ts:1114`; assumption documented at `kit.command.ts:515-517`). A concurrent adjustment can append stock between the kit create's reads and commit, leaving a kit SKU with on-hand stock that no command can ever remove (all three +stock writers refuse kits; orders explode past it). Both guards read each other's uncommitted state; neither blocks the other. — [BE] refs above.

### Medium

- **F3 (BE, medium) — Snapshot type mirrors are comment-guarded only; silent-add drift compiles cleanly.** The SKU arm is mirrored in three places (`catalog.facade.ts:103-144` `SkuSummary` → `receiving.facade.ts:64-87` → `receiving.dto.ts:449-503`) and the pick-task arm in two (`pick.command.ts:224-261`/`getPickTasksInTx` :1612-1710 → `outbound.dto.ts:866-930`) — all field-identical today with zero drift, but nothing fails when a new field is added to the source and forgotten in the mirrors. 11-7 itself hand-added `variantValues`/`axes` in three places and `kitParentSkuCode` in two. Data is single-sourced (the controller spreads facade objects verbatim), so this is a type-lockstep risk, not a runtime one today. — [AD]+[DV], same root.
- **F4 (FE, medium) — `fetchAllPages`' 20-hop cap (~1,000 SKUs) silently truncates the whole-catalog walks** the variant picker and kit markers depend on, while the importer admits 10,000 rows; tail SKUs vanish from `attachCandidates` and kit rows read `—` with no signal. — [FE] `src/lib/fetch-all-pages.ts:17`, `use-catalog.ts:218,274`, `sku-table.tsx:663`; import cap `import.command.ts`.
- **F5 (FE, medium) — Failed products fetch renders contradictory copy**: "Products unavailable" banner alongside the table's "No products yet — create one above." — [FE] `products-card.tsx:175-180`.
- **F6 (BE, medium) — Malformed-UUID refusal diverged three ways inside one epic**, with two commands' comments contradicting their own code: SKU attach answers 400 `validation-failed` (`sku.command.ts:340-344`); product edit answers 404 while claiming parity (`product.command.ts:190-194`); kit create answers 404 while its comment says 400 (`kit.command.ts:110-115`). Same check (in-command UUID_RE backstop, no `@IsUUID` on these params), three sessions, three readings; FE mappers branch on `code`, so client prose differs per surface. — [DV] P1.
- **F7 (BE, medium) — Variant-values parsing has a prototype-chain sink.** Import: `"toString" in values` falsely matches the prototype chain (a valid axis named `toString` is refused with a wrong message) and `values['__proto__'] = v` is a silent no-op (`import.command.ts:1340-1356`). HTTP: `JSON.parse` gives an own `__proto__` key, so `{"__proto__":"M"}` passes `assertVariantValues` but `normalizeVariantValues` (`product.command.ts:474-482`) drops it — the SKU stores values that do not cover the declared axes, violating the "cover EXACTLY" invariant. Pathological input, but the boundary claims byte-exact coverage. — [BE] M1.
