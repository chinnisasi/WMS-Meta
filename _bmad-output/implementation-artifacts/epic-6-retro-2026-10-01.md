**Fix-now candidates (proposed to the human, not auto-applied):**

1. **No flow ever sets `batches.expiry_date` except the manual ledger-intake route** — VERIFIED TRUE (re-checked: `src/modules/inbound/` carries zero `expiryDate` references; `ensureBatchIdentity` at `receiving.command.ts:1157-1196` threads only `code`+`mfgDate`; `catalog.facade.ts` `ensureBatches` is creation-never-edit; mobile's only "expiry" hits are session-badge expiry). Every GRN-created batch has `expiry_date: null` forever → **the FR-23 expiry arm's real feeding path is the manual intake verb alone**, and the 6-2 test suite masked this by seeding expiry via `adjustBatch`. A tenant reading the panel's "Expiring within N days" cannot tell that GRN stock never alerts. The per-story reviews could not see it because each review read the scan against seeded batches, not the intake surface. → action item: PENDING row + module-doc gotcha + an Epic-9-prep note that the bell panel must not promise receiving-fed expiry coverage; the capture itself (GRN line DTO `expDate` threaded through `ensureBatchIdentity`, or the awaited catalog batch-edit verb) is a real future story.
2. **The expiry arm has no off switch for an already-configured tenant** — VERIFIED TRUE (`replenishment.command.ts:906-918`: "There is no DELETE… a tenant that wants the arms effectively off writes wide values"; no delete verb; `0 stays a threshold, not an off switch`). The "wide values" disable story works for aging (huge threshold) but is inverted for expiry — a wide lead makes MORE batches qualify, and lead=0 still leaves every already-expired batch alerting (the documented "expiry only matures" semantics). Once upserted, a tenant cannot disable expiry alerting without support. → comment-truth fix + PENDING row next to the FE-editor deferral.
3. **Phase 1 of the expiry scan computes a full `batchScopeSumsInTx` aggregate whose result is dead** — VERIFIED TRUE (`replenishment.expiry.scan.ts:96-101`: only `enumerated === null` is tested; phase 2 correctly re-reads fresh). A discarded per-warehouse GROUP BY on `batch_on_hand` every tick, every scope, plus a comment block that reads as though the enumeration feeds the scan. → smallest fix: reduce phase 1 to the config read; the e2e arms observe nothing from the phase-1 sum.
4. **Comment-truth bundle** — the `codeByBatch.get(entry.batchId)!` comment ("Every alert row FKs its batch… leans on that database guarantee") — VERIFIED TRUE: `0049_expiry_alerts.sql` has no FK (the module's no-FK convention; snapshot records `foreignKeys: {}`); the real guarantee is "no command deletes batch rows" (verified: the only batch-flavored delete is the `batch_on_hand` projection row at `ledger.service.ts:1641`). Same class as the 2-2 review round's comment-order finding. → reword to the true guarantee.
