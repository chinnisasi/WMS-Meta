## Intent

**Problem:** Stock accuracy has no enforcement loop: nothing counts what is actually on the shelf, so shrinkage, damage and misplacement surface only as stockouts. Epic 5 requires cycle counts — generated by ABC class and schedule plus on-demand — executed bin-by-bin on mobile with no operations freeze, where counted ≠ expected creates a variance record, never a silent write-off.

**Approach:** Stored count tasks (one per bin) whose per-SKU expected quantities and `binStateEpoch` are captured at task start; on-demand creation plus a scheduler worker generating due tasks from per-warehouse ABC policies; mobile execution through the existing inbox Count tab (snapshot `countTasks` arm → scan → qty stepper → one `count.submit` op); variance records written at submit with the epoch conflict flagged — resolution is 5-4's job.

## Boundaries & Constraints

**Always:**
- Expected quantity is the bin state **at count start** — captured into the task rows when the task is created, never recomputed at submit.
- The epoch compare runs **under the locks** (read → bin/warehouse lock → compare — movements gotcha 2); the submitted epoch is compared for equality against the live epoch, `null` matches.
- Concurrent movement during counting is **flagged, not lost**: an epoch mismatch marks the variance record with the conflict rather than dropping or auto-applying anything.
- Counted ≠ expected creates a variance record with status `open` — 5-3 **never writes stock**; no ledger event, no adjustment.
- Counts never block other operations — no count lock on a bin's stock.
- All mutating endpoints: idempotency key (ULID) replay with hash-mismatch rejection, key written LAST; validation 404/400 before any write; permission asserted at command-service entry before replay lookup.
- New capabilities follow the floor-verb pattern and carry the "Mirrored into wms-fe `src/lib/users.ts`" comment.
- New tables follow the repo conventions: uuidv7 PKs, bare-uuid FK-less refs, `...tenantTimestamps`, CHECKs + RLS **only in migration SQL**, module-exclusive tables.
- Any new list cursor uses `fullPrecisionInstant` encoding (gotcha 19).
- Snapshot `countTasks` arm is additive with the seal-defaulting pattern (absent key = older seal → `[]`).

**Never:**
- No write-off, stock write or ledger write in 5-3 (variance resolution and stock correction are 5-4/5-5).
- No batch/serial-level count reconciliation in 5-3 — variance is SKU-level; batch/serial detail is later scope.
- No web admin UI beyond the capability mirror (policy/count admin surfaces are deferred).
- Movements never projects stock tables directly.
- Do not modify transfer tables/routes/facade exports, the 0043 migration, adjustment vocabulary, or `transferTasks` snapshot composition.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| On-demand count created | POST with bin, `counts.manage`, open task absent | Task `pending`, per-SKU expected + epoch captured in-tx under locks; outbox `count.created` | 404 unknown bin; 400 validation-failed — system bin (counts target storage bins only); 409 task already open on bin; 403 role-denied |
| Scheduler tick, policy due | Storage bins with class-A skus past interval, no open task (system-owned bins excluded) | Tasks created in batch (system actor, warehouse lock); no task for bin already counted within interval or with open task; outbox events | Partial failure → whole tick rolls back, retried next interval |
| Submit, epoch unchanged, counted = expected | `count.submit`, all lines counted equal | Task `completed`, no variance record | — |
| Submit, epoch unchanged, counted ≠ expected | Some line differs | Task `completed`; variance rows (`open`) per differing SKU with expected/counted/delta | — |
| Submit, epoch mismatch | Live epoch ≠ task epoch (pick/receipt ran during count) | Task `completed`; variance rows flagged `epochConflict` AND a fresh recount task auto-created for the bin in the same transaction | Conflict is surfaced, never silently applied |
| SKU found in bin beyond task lines | Counted skuId has no task line | Line appended with `expectedQuantity` 0; counted > 0 → variance row (expected 0) | Counted == 0 → line recorded, no variance |
| Submit with uncounted lines | Any task line lacks `countedQuantity` | Submit refused — 0 is a valid count only when explicitly entered | 400 `count-incomplete` |
| Mobile replay of same op | Same ULID Idempotency-Key, same body | Replay serves stored snapshot byte-identical | Hash mismatch → 422 idempotency-key-reuse |
| Floor verb, device session | `AnySessionGuard`, `userId === null` | badge-in required (401), actor = device badge | Same as inbound-confirm arm |
| Policy write | PUT policies, `counts.manage`, non-null fields | Upsert one row per (tenant, warehouse, class); replay-aware | 400 validation; 409 unique-violation race loser |
| Null ABC class | SKU with `abc_class` unset in a scheduled bin | SKU excluded from scheduled generation (on-demand counts still cover its bin) | — |

**Decisions (from planning questions, 2026-09-28):**
- **OQ-1 — ABC class source:** nullable `abc_class` ('a'|'b'|'c') column on `skus`, set via a new OPTIONAL `abc_class` column in the catalog import header (header contract + row parser grow together, the 11.3/12.1 precedent) and via sku edit. Count policies reference the class; `null` = excluded from scheduled generation, still countable on demand.
- **OQ-2 — epoch-mismatch submit:** variance rows flagged `epochConflict` **and** a fresh recount task auto-created for the same bin in the same transaction (AD-14 case-3 re-plan shape). Recount generation is bounded by the same open-task-per-bin rule.

**Acceptance Criteria:**
- Given a bin holding a class-A sku past its interval and no open task, when the scheduler ticks, then a `pending` count task exists with expected quantities and epoch captured, and an outbox `count.created` event exists.
- Given an open count task, when the same `count.submit` ULID replays, then the stored snapshot is re-served byte-identical with no new variance rows.
- Given a pick bumps the bin epoch between task start and submit, when the count submits, then variance rows carry the `epochConflict` flag, a fresh recount task exists for the bin, and no stock changes.

## Design Notes

- **Stored tasks, not derived reads.** Putaway/transfer tasks are derived on read, but a count task must freeze its expected quantity and epoch at creation — a derived task recomputes them, breaking the "expected = bin state at count start" rule. Hence `count_tasks` is the movements module's first stored task table.
- **Movements, not inventory.** `docs/design/modules/movements.md:9` names cycle counts as growing in movements (5-2's adjustments-in-inventory is a divergence, not precedent). Counts write no stock, so no inventory-write seam is needed.
- **Variance vocabulary in 5-3 is exactly `open`.** 5-4 owns resolution states; 5-3 inserts and never updates a variance row afterwards.
- **AD-14 mapping:** the epoch compare at submit is the same mechanism as `confirmInbound`'s `transfer-bin-changed`; the count's "conflict" arm is deliberately softer because counting is observational — the operator's numbers are still valid observations, only the expected baseline moved.
