# Epic 5 Context: Moves, Counts & Approvals — Variance With an Explanation

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Give operations a controlled way to move stock and correct it: Transfer Orders with a real in-transit state so stock in motion is never sellable at either end; reason-coded adjustments gated by configurable approval thresholds; ABC-scheduled and on-demand cycle counts executed bin-by-bin on mobile while normal operations continue; and a variance-review flow that ends every discrepancy in an explained, audit-logged resolution rather than a silent write-off. A single consolidated human-review queue (Conflicts & Reviews) collects everything needing human judgment — quarantined replay conflicts, over-receipt approvals, escalated variances — so nothing is buried inside a module. Realizes the counting half of UJ-4 (close the month with a clean count: variance found on mobile, explained from the ledger, approved with a reason code, in minutes).

## Stories

- Story 5.1: Transfer orders
- Story 5.2: Stock adjustments with approval thresholds
- Story 5.3: Cycle count scheduling and execution
- Story 5.4: Variance review and resolution
- Story 5.5: Conflicts & Reviews — the human-review queue

## Requirements & Constraints

**Transfers (5.1).** Bin→Bin and Warehouse→Warehouse moves execute as a two-sided event — outbound confirm, then inbound confirm — with an in-transit state between them. In-transit stock is excluded from ATP of both source and destination until inbound confirm. Each leg writes its own ledger events correlated by Transfer Order ID. Transfer-confirm is a mobile task type in the operator inbox.

**Adjustments (5.2).** An authorized user adjusts stock with a reason code, always as ledger events. An adjustment beyond a configurable quantity/value threshold requires Owner approval: it sits pending, cannot change ATP while pending, and the approver is notified. Every adjustment is traceable to actor, reason, and the ledger events it produced; approval/rejection is itself audit-logged.

**Counts (5.3).** Count tasks are generated by ABC class and schedule, plus on-demand counts, executed bin-by-bin on mobile with no operations freeze. A count task's expected quantity is the bin state at count start; concurrent picks/receipts during counting are flagged, not lost. Counted ≠ expected creates a variance record — never an immediate silent write-off.

**Variance review (5.4).** A variance routes to the configured approver with the bin's ledger history attached. Resolution is approve-adjust or recount; the resolution references the ledger events considered and is audit-logged; a recount replaces the variance's expected basis with the recount snapshot. Variances over threshold route to the Owner with notification.

**Human-review queue (5.5).** One queue for quarantined replay conflicts (AD-14 case 4) and pending approvals: it shows the quarantined event with its on-device snapshot, server state, and ledger context side by side; resolution (apply / recount / discard-to-audit) writes to the audit trail; batch-resolve works for similar conflicts. Over-receipt approvals (from Epic 3 receiving) and escalated variances land in the same queue. The surface is permission-gated and hidden — not blocked — for roles without access.

**Success signal.** Count variance value (absolute variance as % of inventory value at monthly close) trending down per tenant validates this epic. Adjustment count is a counter-metric: never minimize it directly — fewer adjustments can mean hidden write-offs; pair with variance value and audit-trail usage.

## Technical Decisions

- **The `movements` module owns transfers, adjustments and cycle counts.** It depends on the inventory module for quantities; it never mutates stock outside ledger events. All state change enters through the shared command layer — API, mobile replay, and scheduler included — so approval gates and role checks cannot be bypassed by any mutation path; authorization is re-evaluated at command-service entry against the current role epoch, never trusted from token claims.
- **In-transit is a derived projection over transfer-correlated ledger events**, like on-hand, ATP and QC-held — not a separately maintained quantity. Replay-reconciliation must reproduce it.
- **Quantities are scaled integers in milli-units** (base UoM × 10³, stored `bigint`); each UoM declares its real decimal precision (≤ 3 dp) from a controlled vocabulary, and decimal conversion happens only at the API and UI edges. A quantity below the declared precision is rejected, never silently rounded. Every ledger event's quantity is signed by movement direction, never by convention.
- **Concurrency safety on bins:** per-bin `state_epoch` captured at task start; the four-case conflict taxonomy (quantity unchanged → apply; reservation still valid → settle; bin moved on → re-plan; unresolvable → quarantine to human review). Bin on-hand never goes negative — a violating event is rejected or routed to review, not written. Offline work settles pre-reserved task stock only; granting new ATP is always an online operation.
- **Idempotency keys (ULID) on all mutating endpoints** — transfer legs and adjustment commands included; ledger events are hash-chained with a WORM anchor; tenant + warehouse scope on every row and access path.
- **Approval thresholds are configurable per-tenant configuration**, not code; the pending-over-threshold state is durable, and the approver is notified (notification surface arrives fully in Epic 9 — a functional entry here is enough).

## UX & Interaction Patterns

- **Approval card** (web): pending adjustment or variance with reason code, threshold context inline, a ledger-history link, and approve/reject/recount actions. Over-threshold items route to the Owner.
- **Review queue item** (Conflicts & Reviews): quarantined event with on-device snapshot, server state, and ledger context side by side; resolve actions write to the audit trail; batch-resolve for similar conflicts.
- **Ledger timeline component**: vertical event list (event type, signed qty, actor, time, reference-doc link within ≤ 2 navigations) — used in variance review and approvals so "why is this number what it is" is click-through, not an export.
- **Mobile count and transfer-confirm flows** are task types in the existing inbox (All/Pick/Putaway/Count/Transfer switcher); counts use the glove-usable qty stepper with manual entry as a deliberate one-tap fallback at every scan step; the four-state scan banner governs every scan.
- **Fractional quantity display and entry:** quantities render at the UoM's declared precision, never storage precision (`18.4 kg`, never `18.400000`); a sub-precision entry is refused inline naming the precision, never silently rounded. Each-counted UoMs keep the integer stepper.
- Web lists follow the dense data-table pattern (cursor pagination, sticky header, tabular numerals, async export for big pulls).

## Cross-Story Dependencies

- **Epic 2 (hard dependency):** the append-only ledger, derived quantities, replay-reconciliation and the hash chain are the substrate every event here rides on; replay-reconciliation is the oracle that in-transit and adjustment projections are correct.
- **Epic 3 (hard dependency):** the mobile client substrate — device enrollment, badge-in, task inbox, camera/HID scanning, the four-state scan banner, offline outbox — is born in story 3.2; transfer and count tasks extend that inbox rather than inventing a second surface. The 5.5 review queue absorbs over-receipt approvals created by 3.3, so 5.5 should land with (or after) that flow exists to feed it.
- **Epic 10 (hard gate, blocking):** fractional quantities in milli-units. Epic 5 built on the old integer model would all be rewritten — build every transfer/adjustment/count quantity path on the milli-unit model and declared precision from day one.
- **Epic 12 (preference, not a gate):** storage classes and the location model land before Epic 5 so counts and transfers are built once against the finished location model; counting bins works without them — the revisit point arrives when non-bin locations (yards, tanks) come in Epic 20.
- **Epic 4 / AD-14:** quarantined replay conflicts from offline picking are the first residents of the 5.5 queue — the queue's data model must accommodate them, not just variances and approvals.
- **Epic 9 (downstream):** variances, adjustment approvals and reconciliation alerts surface as notification-panel entries and in the audit trail; keep events rich enough (actor, reason, reference document) for those surfaces to aggregate.
