## Intent

**Problem:** Ops the server refuses at outbox replay (`rejected` and AD-14 case-4 `quarantined` fates) are deleted from the device's durable outbox (`engine.ts:126-134` → `replaceOps` at `:227`) and survive only as an in-memory sync-summary line — an app restart erases them, the server has no record at all, and `kit-cannot-hold-stock`/catch-weight refusals currently land there only by fall-through accident. A physically real scan can vanish with no durable trace on either side, and nobody can review it.

**Approach:** Make the retraction durable end-to-end: the device moves every dropped terminal op to a local retained table (instead of deleting it) and uploads a sync report of them to a new backend `rejected_ops` table; a web Conflicts & Reviews tab lists them and resolves each with apply (re-execute the stored payload through its own guarded command, the staleness token dropped but every other guard live), recount (mint a count task on the affected bin, the movement recount path), or discard-to-audit. The mobile hardening batch ratified at the epic-5 retro rides in this story's mobile slice.

## Boundaries & Constraints

**Always:**
- Resolve and upload carry a fresh ULID `Idempotency-Key`; same-key same-payload replays re-serve the stored outcome, 422 on reuse with a changed payload.
- Apply is never a force-write: it re-executes the stored payload through the op's own command path under the op's attributed operator — the server re-reads that operator's current role and device status at apply time — with every guard live (stock, holds, premises, role, kit rule); the resolver is named in the audit as its judge. Any refusal surfaces verbatim and the row stays open.
- Resolution is gated on the existing `review.decide` capability (owner + ops_manager) — no new capability, the mirror stays at 31.
- Upload is automatic after every replay pass that produced drops, plus the existing manual Sync button; a failed upload leaves the rows retained for the next pass.
- Zero-scan-loss holds through the new path: a dropped op is durably retained client-side in the same transaction that removes it from the outbox, stays there until the server acks the report, and decrypt failures skip-with-note rather than silently vanish.
- Upload is at-least-once with per-row dedupe on (tenant_id, op_id): a re-posted row updates nothing, a replay report is a no-op.
- Every resolve arm writes audit + outbox events (naming the original operator attribution, device, and refusal code) — nothing here lands unexplained.
- Mobile: the report upload joins the replay-gate single-flight; the four-state sync summary keeps rendering unchanged (retention is additive, never a behavior change of the existing screens).

**Never:**
- No auto-apply, no batch resolve, no force/override arm — human judgment only, one row per click.
- No change to the existing review-queue tab conventions: capability gate hides-never-blocks, no decision-note field, no requester notification.
- No mutation of the server-side command guards or the AD-14 taxonomy itself; the queue consumes refusals, it does not re-classify them.
- No local deletion of retained rows before the server acks; no upload of `self-test.echo` ops (device diagnostics, not reviewable).
- No ledger-write shortcut for the recount arm outside the existing `createRecountTaskInTx` movement core.
- No recount offer for `binId`-less payloads (pack, grn) — the arm is hidden client-side, never a served 409.

## Code Map

- **Uploader failure semantics (Spec Change Log 2026-09-30, triage Entry A — load-bearing for re-derivation):** the retained-report uploader must make progress past a whole-report refusal. When a report is refused 400/422/413-or-any-4xx/5xx without an ack, rows stay retained (frozen Never rule — no local deletion before an ack). When the refusal is a boundary 400 whose problem detail names a specific row (opId), the uploader isolates that row: it removes the row from the batch for THIS and all later passes (a locally-marked `record-refused` state on the retained row — never a deletion), keeps a permanent note in the sync summary, and re-uploads the remaining rows immediately. Each retained row therefore has exactly two terminal states: acked (reported → rows deleted) or record-refused (marked + noted, never retried, never deleted, never re-uploaded). Transport/status failures that do NOT name a row (network, 401, 413, 403, 500) retry the whole batch next pass (frozen Always rule). The uploader must also bound each report by the server's real body limit, not just row count: slice retained reports at 50 rows per POST (the 200-row cap stays the per-row-dedupe/table ceiling, not the upload slice). Additionally carried (moot-but-carried patch entries): per-report timestamp instants validated at both the recordSyncReport boundary and the apply-arm opTime normalization with `assertUtcIso`'s strict UTC-ISO contract (normalize-then-assert both `payload.occurredAt` and row stamps); reporter attribution stamped PER ROW (badge-in deviceId/operatorEmail merged with each row's own sealed opDeviceLabel/opOperatorEmail); FE recount probe reads `binId ?? toBinId`; `RejectedOpListQuery.limit` gets `@IsNumber` + `@Min(1)` + `@Max(200)`.

## Design Notes

- **Module ownership is tenancy deliberately.** The resource is a report of a device sync outcome, op-type-generic across receive/pick/putaway/pack/count/transfer — no other module owns it. Tenancy already owns the device contract (enroll, badge-in, catalog snapshot, self-test echo); the review.decide gates follow the excursion-queue precedent. Cross-module re-execution goes through the owning command services (API, mobile replay, scheduler, and now human review are all entry surfaces of the shared command layer), never around them.
- **Apply drops only the staleness token.** The mobile design declares binStateEpoch "a timestamped observation, not a decision" — the human judgment replaces that observation; nothing else (stock, holds, cancelled premises, role, kit rule) is overridden. A permanently-refused op (kit rule, catch-weight 400) refuses verbatim on every apply and closes only via discard — honest queue behavior, not a defect.
- **Ordering inside a replay pass:** drops are retained in the SAME SQLite transaction as `replaceOps` (no window where an op exists in neither), then the report uploads after the pass under the replay gate; upload failure leaves rows retained for the next pass. Per-row (tenant, op_id) dedupe makes report replay a no-op, so at-least-once is safe server-side. **Row-named refusal isolation (Spec Change Log 2026-09-30):** a boundary 400 naming a row is not an ack, so the row itself is never deleted — it is locally marked record-refused (sticky, never re-uploaded), noted in the summary, and removed from the batch so the rest of the report makes progress; no other row ever starves behind a row the server will never record. Reports are sliced at 50 rows (server body-limit bound); dedupe stays the server-side safety net.
- **Retro fold-in provenance:** the two classification arms, the count scan/double-tap guards and the wire tests are epic-5 retro action item 1 folded into this slice by human ratification 2026-09-30.
