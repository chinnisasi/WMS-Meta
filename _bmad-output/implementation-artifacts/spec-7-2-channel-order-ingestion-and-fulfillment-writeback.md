## Intent

A channel order ingests idempotently from a marketplace webhook into THE order path (4-1's `createOrder`, `source: 'ingested'` — verification and mapping resolve ahead of it), the connection's `backorder_policy` is consumed at acceptance for the first time, fulfillment/dispatch/cancel statuses write back to the channel through the same outbox-and-port machinery 7-1 established, and a channel-side cancellation releases the order's holds atomically through `cancelOrder`. Shopify's ports land as real HTTP transports (FQ-3, user-answered in 7-1: 7-2 bears the HTTP client + retry/backoff); the load-test harness that pins NFR-2 (15× median order rate for 2 hours, zero oversell, no pool deadlock) ships here and its run is recorded — it is the epic's closing verification. The Channels surface gains the ingestion config 7-1 left facade-only: per-connection SKU mappings and the ingest warehouse.

Nothing here weakens any standing arm: acceptance and reservation continue when a channel API is unavailable (webhook receipts are channel-initiated; writeback failures degrade the connection the way sync failures already do).

## Boundaries (out of scope)

- **No order-amendment ingestion.** A channel payload whose mapped content diverges from the stored hash answers `422 order-source-conflict` and nothing else — there is no edited-order flow, no line-quantity update onto an accepted order.
- **No refund, return or RTO flows** — a channel cancel arriving after our order left `accepted` is an ACK-no-effect, never a reversal path.
- **No marketplace transports beyond Shopify.** `amazon-in`/`flipkart` keep the typed verbatim 501 on every arm, ingestion included — the epic's stated fallback (partner-API approvals may slip; Shopify + manual first, marketplaces fast-follow). PENDING row recorded; a transport is additive (registry + arms).
- **No notification/bell panel** (Epic 9 reads the KPIs), **no mobile surface** (epic decision), **no ingest-failure review surface** — refused ingests trace through `integration_calls` meter rows and audit only; a review queue is the 5-5 shape re-derivable later.
- **No multi-warehouse order routing** — one ingest warehouse per connection (RD-4); order assignment per-warehouse-by-quantity is a later epic's arithmetic.
- **No per-tenant breaker/SLO config** — the 7-1 frozen consts stand.
- **The load harness is a script, not an ops capability** — no scheduler, no dashboards; "load-tested before every peak season" stays a PENDING ops note after the recorded run.

**Always:**

- Signature verification is a precondition for ANY effect — there is no unverified ingest (AD-5). Verification runs over the RAW body before any JSON parse; the secret never appears in a refusal, a log, or a meter row.
- Manual + channel ingestion stays ONE path: the webhook handler resolves mapping lines and calls `OutboundFacade.createOrder` / `cancelOrder`; it never writes an orders table (AD-6 — outbound owns the machine exclusively).
- The adapter never writes stock or order state directly (`channels.md` standing rule) — all quantity and hold moves ride InventoryFacade/outbound passthroughs.
- The order state machine is untouched — every guard is an allow-list, no status arm changes; `orderNotAcceptedRefusal`'s exhaustiveness switch stays the only hand-classified site.
- A writeback that fails is a degraded connection, never a wedged order — nothing in the order path waits on a channel (7-1's boundary stands).

## Resolved decisions

- **RD-1 — the ingestion identity is the channel's order identity, not the transport's delivery id.** The parse arm sets `externalEventId :=` the channel order ref (Shopify's payload `id`; the delivery/notification id is NOT stable across the topic's lifetime in the way the dedup needs). Dedup, hash divergence (`422 order-source-conflict`) and the concurrent-loser release ride 4-1's machinery verbatim (the partial unique `orders_source_event_unique`, the pre-check `order.command.ts:402-436`, `resolveDedupLoser :1028` which releases the loser's grants `:668`). The parse arm NORMALIZES the payload to exactly what the order captures (order ref, destination, per-line externalRef + quantity) before the command hashes it — non-material channel-side noise (tags, notes, timestamps) never re-hashes, so a marketplace's own re-notification of an unchanged order replays to the first order.
- **RD-2 — the ingestion's actor is the connection's `connected_by`.** The facade's authority is the DB role re-read at command entry (`order.command.ts:312`); a webhook carries no session, so ingest passes `actorUserId = connected_by` — the account that connected the channel, which held `channel.manage` (Owner/Ops Manager) and therefore holds `orders.manage`. An actor that has since lost `orders.manage` fails the command closed (403-shaped) — the delivery NACKs, the channel retries, and the remediation is re-connecting with an eligible account. Audit rows carry that actor with the payload noting the channel source.
- **RD-3 — `backorder_policy: reject` is a whole-order post-grant refusal.** `createOrder` gains an optional `backorderPolicy` field (default `'accept'` — every manual caller unchanged). Under `reject`, after phase-2's grants and before the write tx opens: ANY line where **granted < demanded — a zero-grant (fully backordered) line included** → `releaseAll` + `BackorderRejectedError` → the webhook answers `409 order-backorder-rejected`, no `orders` row. The check reads phase-2's granted/demanded **grant map, never order rows** — kit parent rows are inserted `reservedQty: 0` with holds living only on children, so a row-based check refuses EVERY kit order regardless of grant success; children and plain lines are the map's entries. The check sits AFTER the grants (never a pre-probe) so no TOCTOU window can refuse what would actually have granted, and the release is the exact machinery the 503 path already runs (`:1006`, fail-safe toward understated ATP, never oversold).
- **RD-4 — ingest warehouse is connection config (`integrations.ingest_warehouse_id`, migration 0051, nullable).** `channel_mappings` stays externalRef → SKU (no warehouse dimension — 7-1's frozen shape); an ingested order lands on the connection's configured warehouse; ingest while unset refuses `422 ingest-warehouse-unset`; the config PUT (row 3) sets/clears it. Availability publish is unchanged (it enumerates all mapped scopes regardless).
- **RD-5 — webhook verification is registry-declared, secret is a credential field, and verification BINDS THE TOPIC.** Each adapter registration gains an optional `webhook` block: `{topics, verification: {header, encoding, scheme}}` and the credential field that carries the secret (`webhookSecret` for shopify — additive to the registry's declared fields; a pre-7-2 connection acquires it by the ordinary rotate). The controller resolves the connection, opens the request-scoped plaintext (`openCredentialForAdapterUse` rules — never logged/persisted/responded), verifies over the RAW body before any parse, **and requires the provider's topic header (e.g. `X-Shopify-Topic`) to match the endpoint's registry-declared topic** — an HMAC-valid body replayed across endpoints or with a mismatched topic is the same verification failure: `401`, no payload naming. A secret that is absent or unopenable (a pre-rotate connection) is the same 401 posture, but NOT silent: verification failures (sig-invalid, topic-mismatch, verification-unconfigured) each meter a coarse, rate-limited `order-ingest` row whose status reads `verification-failed` — the body's content is never named. Reason: a dropped `webhookSecret` (rotate re-supplies the credential blob wholesale — `validateCredential` stores exactly the supplied fields) can otherwise 401 every delivery for days with health green and no counter moving, and Shopify's endpoint policy DELETES a persistently-failing webhook — misconfiguration must be observed the day it starts. The stored blob's other fields (shopDomain, accessToken) are unaffected by ingest. A scheme-less provider's endpoint answers the typed 501 (Amazon.in/Flipkart — their schemes are not invented spec-side).
- **RD-6 (amended, human-renegotiated iteration 2) — real transport scope: Shopify, and only Shopify.** The availability publish resolves `skuId` → Shopify `inventory_item_id` before posting: at publish time the arm looks the mapped SKU's variant up by `externalRef` through the Admin API and caches the resolved `inventory_item_id` per connection/scope; an unresolvable variant (or a lookup failure) refuses the upload with a typed, METED refusal and no breaker/health movement — the WMS uuid is never posted as a Shopify id. Posted availability is quantized `floor(visibleMilli)` — Shopify inventory is integer-only and floor is ATP-safe (never advertises more than exists).  `channel-http.ts`: `fetch` (the bun runtime — no new dependency) with `AbortSignal` timeout (`CHANNEL_HTTP_TIMEOUT_MS`, default 10 000), retry policy carried by the OUTBOX RELAY (the retry/backoff utility FQ-3 named — nothing hand-rolls a second one), credential and body content never logged. The Shopify arms replace their `unconfigured*` registrations: availability publish (inventory set per mapped scope — the `ChannelAvailabilityScope` payload is already the port's), revoke (a best-effort attempt, the disconnect's existing non-blocking posture), the NEW writeback, and — because a fulfillment call without it is un-answerable — shopify's registry gains the OPTIONAL credential field `locationId` (the Shopify location the writeback fulfills against; one per connection since a connection IS a shop). Writeback with `locationId` unset fails the attempt with the named outcome `writeback-location-unset` (metered, never retried past the relay's budget, remediation = rotate) — the location is not guessed from the channel's location list. Webhook subscriptions are registered MERCHANT-side (Shopify admin: topics + the copyable URLs row 6 surfaces) — the topics declaration's wire consumers (endpoint topic-binding + the 501 gate) ship here, API-side subscription management is a PENDING row, not silently absent. Connection health turns honest for shopify (it read degraded-from-transport since 7-1); amazon-in/flipkart stay 501-degraded (PENDING).
- **RD-7 (amended, human-renegotiated iteration 2) — the writeback consumer re-reads, never trusts; dedupe is STATE-SPECIFIC via provider read-back; writeback is breaker-DECOUPLED from sync.** The arm sends the RIGHT line set: any fulfillment line whose SKU has no live mapping fails the WHOLE attempt with a typed 422-shaped metered refusal (never retried past the relay's budget; remediation = the mapping PUT) — the channel never sees a partial fulfillment; kit parent lines are excluded from the arm (their exploded children carry the shipped quantities), so a mapped parent is never posted alongside its children. `ChannelWritebackDelivery` (the `channel-availability.delivery.ts` shape): the relayed event names the order; the handler re-reads the order row (its channel arms live there), skips-and-acks when the connection is gone (the 7-1 handler's existing gone-arm — verified: `integrationForDelivery` null → ack), and calls the writeback arm with the live snapshot ("kind", order, lines, and for dispatch the carrier/tracking). The at-least-once relay means the arm must tolerate a repeat — the read-back guard is PER STATE, not "an existing fulfillment": **packed** posts only when no fulfillment exists; **dispatched** updates the fulfillment that exists WITHOUT tracking, acks when tracking is already present; **cancelled** acks when the channel already holds cancellation. The packed/dispatched arms are defined against each other — a relay reordering that runs dispatched before packed settles converges (dispatched writes tracking on the just-created fulfillment; the packed redrain then reads tracking-present and acks). The echo loop (channel-initiated cancel → our `cancelOrder` → `order.cancelled` outbox → writeback calls the channel that initiated it) self-settles by the cancelled-state read-back at the cost of one idempotent no-op call — pinned by test, not treated as a defect. Writeback settle: meter rows kind `order-writeback` + the relay's own retry/DLQ budget ONLY — a writeback outcome NEVER moves `last_synced_at`, `last_error`, `consecutive_failures` or the availability breaker (`recordDelivery`'s arm hardcodes the sync stamps — verified — so writeback gets its own settle arm). Coupling back would stop availability publishing exactly at flash-sale peak, when stale channel quantity is most dangerous. The residual window (call lands, relay dies before ack) is at-least-once currency — the read-back shrinks it to the sub-second crash window; recorded honestly, not solved.
- **RD-8 — a channel cancellation is applied only to an `accepted` order; an UNKNOWN order is a NACK, not an ACK.** The ref is Shopify's immutable order `id` (merchants can recreate `order_number`/`name` — the parse arm pin makes that choice enforceable). Resolve the order by (integration, external event id); **unknown → `503 cancellation-unresolved` NACK** — the channel retries; a cancellation racing the create's commit (webhooks share no ordering guarantee) resolves on the retry milliseconds later instead of being lost forever, and a ref that NEVER resolves is abandoned by the channel's own retry budget — safe because an order we never created holds nothing to leak. `accepted` → `cancelOrder` through the facade (its guards govern; a drawn/committed refusal surfaces as an audit-recorded ignored outcome, never a wedge). Any other resolved arm (already `cancelled`, `ready_to_dispatch`, `dispatched`) → ACK `ignored` — the reversal flows are out of scope, and the state machine's refusal is the honest answer. Every cancellation outcome lands in the meter (kind `order-ingest`, event-shaped detail) and an audit row.
- **RD-9 — ingest is processed synchronously in the HTTP handler, and the handler's budget is UNDER the channel's timeout.** No inbound queue: verify → parse → command, answer one decision. The channel's own retry budget plus the dedup machinery (RD-1) make every redelivery safe, including the timeout-with-committed-order case (the reply is lost, the retry replays). The p95 budget is therefore **≤ 4 s with a > 5 s fraction of 0** — Shopify's webhook timeout is ~5 s, and an answer slower than that is a guaranteed load-AMPLIFYING redelivery (concurrent same-payload processors doubling grant contention at exactly the contended SKUs — NFR-2's opposite). The grant store's 503 answers the same NACK — fail-closed, nothing written. The ingest meter contract (T3): `order-ingest` rows NEVER touch connection health, breaker counters or the sync stamps — refused outcomes (`rejected|conflict|unmapped|verification-failed…`) meter as statuses, not failures; expected row volume at 15×/2 h is bounded by the run's own report.
- **RD-10 — the load harness measures the whole machinery, not a mock.** Real HTTP against a booted app (`createApp(true)`) with a seeded tenant, real webhook deliveries at 15× a configurable median order rate PLUS a concurrent adjustment stream (on-hand churn is the mechanism oversell hides in — a steady-state workload cannot produce one), driven by a PINNED client (bounded connection pool, per-request timeout ≥ the p95 budget, wall-clock pacing — achieved-vs-target rate reported, because client silent under-delivery or burst amplification both distort what "15×" means). Gates: accept-p95 ≤ 4 s, > 5 s fraction 0, writeback lag REPORTED (median/max — soft, not a gate), "zero oversells" DEFINED CONCRETELY: per (warehouse, sku) at every journal point Σ held ≤ on-hand − committed, plus the post-run re-derivation flagging any accepted order whose grants exceeded dispatchable headroom at grant time (journal/counter parity alone cannot see this — a fully-parity ledger can still contain accepted orders that never had dispatchable stock), no pool deadlock (no request left uncompleted past a bound). The recorded run names its environment (local compose Postgres + Valkey, default pool config, committed harness flags); a mid-run crash gets ONE bounded restart, after which the smoke mode + partial report are committed with the failure noted — the evidence must be reproducible from the committed script, not a local anecdote. The 2-hour run is the epic's recorded evidence; a shorter smoke mode exists for CI.

## Design Notes

**RN-1 — why the dedup identity is the order ref, and what the payload hash covers.** AD-5's "(integration, event ID, signature-verified payload hash)" is implemented exactly as 4-1 already shaped it: `external_event_id` (the channel order ref under RD-1 — immutable Shopify `id`, never `order_number`) + `source_payload_hash` (the MAPPED content — warehouse, destination, skuId+base-quantity lines — hashed post-parse; the raw channel payload is never stored or hashed). This is the load-bearing normalisation: a marketplace re-notification of an unchanged order (retries, `orders/updated` churn that touches nothing material) hashes identical and replays; a real divergence refuses. The parse arm owns the normalisation; the raw payload is never retained, and the divergence answer is 422 (the delivery refuses itself), never a wedge into retry. **Two consequences the design accepts on the record:** (1) the dedup is ETERNAL — `orders_source_event_unique` is not status-scoped, an accepted order owns its ref forever, so a redelivery of a since-cancelled order answers `200 replayed` with the stored snapshot; no re-ingest of the ref exists and none is wanted (refs are immutable). (2) the hash covers CONFIG-RESOLVED content — the ingest warehouse and mapped SKUs — so an operator's mapping re-point or a warehouse change makes in-flight channel redeliveries answer `422 order-source-conflict` (or `400` for a cleared mapping) for as long as the channel's retry queue lasts (~19 attempts / 48 h). These are CONFIG SHADOWS, not tampering: they meter as `order-ingest` statuses (bounded by the channel's own budget), never as health failures or breaker rungs, and the ordinary remediation (fix the mapping, let the retry land, or manually re-push from the channel admin) needs the redelivery to be refused-now-and-retried, which is exactly the NACK posture both arms keep.

**RN-2 — why post-grant policy checking, not pre-probes.** A reject-policy pre-read of ATP would refuse orders the grant would have satisfied (a concurrent release between probe and grant) and accept orders the grant loses (a concurrent consume); only the actual grants are authoritative. After them the outcome is known exactly: any partial line under `reject` releases everything. The releaseAll is the same code the 503 path trusts, whose failure direction is understated-ATP-never-oversold.

**RN-3 — why the actor is `connected_by` and what breaks with it.** The command skeleton's authority is a DB role re-read; there is no session-less actor vocabulary in this repo and inventing one is a cross-cutting decision that a two-story story does not get to make. `connected_by` already held `channel.manage` = Owner/Ops Manager = `orders.manage`. The failure direction is closed (refused, retried, visible on the connection's health/last_error); the cost is an operational one (a demoted/departed connector stops ingestion until reconnect) recorded here so the review cannot discover it as a surprise.

**RN-4 — why Shopify-only transport.** FQ-3 froze "real transport lands with 7-2"; the epic ALSO states the launch-order assumption that marketplace partner approvals may slip and Shopify goes first. Building three untestable-without-credentials transports in one story produces exactly the kind of load the launch story would have to re-validate; Amazon's and Flipkart's arms keep their typed 501s (the machine-read branch is unchanged), the PENDING row carries them, and a transport is one registration + one arm (the registry's additive rule, now proven twice — carriers and channels).

**RN-5 — the writeback idempotency posture, stated honestly.** The relay is at-least-once; the provider read-back guard is a best-effort dedupe, not a proof; the residual window (provider call committed, relay crashed before its ack) survives by design. The carriers' own at-least-once posture accepted the same class. What the design does NOT accept is a duplicate visible to the channel MORE than transiently — the read-back re-checks on every redrain so a redrained row self-heals the dedupe on its next attempt.

**RN-6 — why synchronous and not queued.** An inbound queue adds a worker, a table, a reaper and its own failure semantics to answer a problem (the channel's ~5-second timeout window) that the existing at-least-once + dedup machinery already answers across BOTH parties: our handler takes bounded time (p95 ≤ 4 s with a > 5 s fraction of 0 is the AC the load test pins — an answer slower than the channel's timeout is answered by nobody and re-arrives as load), the marketplace retries politely, and redelivery resolves to the first order. The 503 arm NACKs — a store outage means nothing was written and the retry is the correct path. If a real deployment ever shows retry storms, the admission is "queue ahead of processing", not "async inside the handler".

**RN-7 — the folded PENDING fix rides in T4's story, outside any transaction.** With shopify's revoke arm real, the 7-1 rotate-vs-disconnect window (PENDING channels, 7-1 review 28) becomes reachable: the disconnect's second tx re-locks and deletes as today, and the CURRENT credential's revocation runs after the delete COMMITS (logged, non-blocking; see the Code Map fold-in for why not in-tx).

**RN-8 — the load harness drives real HTTP on purpose.** The 15× gate exists to prove the JOINT machinery (reservation core + sync + ingest) at load; a facade-level harness would skip the Express body handling, the verification, the pool-nesting posture and the connection handling that a 2-hour run at 15× exists to find (the epic-1 lesson: live runs caught what a 212-test suite never observed). Overhead is the point.
