# Offline Floor Seam Review — multi-domain additions (2026-09-17)

The pre-expansion offline contract is solid and internally consistent. The expansion introduces four new *decisions* (conformance, shelf-life, catch-weight tolerance, witness validity) without extending the two things that made the original honest: **a defined on-device knowledge base**, and **a banner vocabulary that matches where each decision is actually made**. Every critical traces to one of those two omissions.

## Critical

**C1 — The cached catalog snapshot has no freshness model, yet four new refusals depend on it.**
Nothing says what the snapshot contains, how old it may be, or what happens when it is stale. The offline-tolerance clock (≥30 min) and the snapshot-age clock are different clocks and the design conflates them — a device can be 5 minutes offline with a 3-day-old snapshot. **False reject:** a bin upgraded server-side after caching fires Rejected, names a rule that no longer exists, offers an alternative computed from stale data — and because "rejected scans never queue" it leaves *no trace at all*. **False accept:** a bin downgraded server-side passes on-device and frozen goods physically enter an ambient bin. *Fix:* add a `Catalog snapshot` state pattern naming required fields (storage class, segregation matrix, shelf-life policy + batch expiry, declared UoM precision, catch-weight tolerance) and a max age; put snapshot age in the refusal microcopy past a threshold; past max age degrade from hard Rejected to amber warn-and-confirm (never green); log every conformance/shelf-life refusal as a queued **audit** event so stale-rule blocking is visible in Conflicts & Reviews.

**C2 — The four-state vocabulary has no slot for a synchronous *server-side* refusal.**
Rejected is defined as an on-device decision. Witness validity is a server fact: an invalid witness badge is not Accepted, not on-device Rejected, not queued ("must never queue"), not Held-for-review (that is a *replayed* op). It has no state — the sharpest honesty violation in the expansion, and it will get built as green or as a modal outside the vocabulary. *Fix:* keep four states, split Rejected's provenance — **Rejected (on-device, ≤500 ms)** and **Rejected (server, online)**, rendering identically, the second naming the server as decider. A server refusal while online is Rejected, never Held; Held stays reserved for quarantined replayed ops.

**C3 — Excursion capture offline is unspecified, and an on-device quarantine badge is a fifth state by the back door.**
Both documents specify excursion *display* and zero excursion *capture* — despite a cold room being the canonical dead zone. If an offline excursion optimistically quarantines on-device, the badge asserts a server-confirmed compliance state the server has never seen, from a component outside the banner vocabulary. *Fix:* add an `Excursion capture` component row (reading queues FIFO, banner shows Recorded · queued); quarantine **should** be optimistic — it is the one fail-safe optimism, withholding rather than releasing stock — but must be labelled as queued and device-local, never mirrored to web as confirmed; and a rejected excursion op must **never auto-release** the quarantine — it becomes a human-release review item.

**C4 — The online-only controlled carve-out is asserted "up front" but no surface delivers it.**
The inbox chips carry no controlled indicator and the task card rules carry no connectivity requirement, so a controlled task is visually indistinguishable and "up front" resolves to "discovered at commit" — exactly what the sentence disclaims. Three unhandled drops: (a) task claimed online then network drops — claim is optimistic and cannot be released offline, so the task is stranded with the one operator who cannot complete it, and there is no `Claim stranded` pattern; (b) drop between witness scan and commit — the witness is present *now* and may not be reconstitutable later, and neither doc chooses between caching the attestation (a queued op whose witness attested to a movement that had not happened) or discarding it; (c) no rule that goods must not move until witnessed **and** committed. *Fix:* controlled marker on the task card and inbox chip with the connectivity requirement; disable controlled cards offline with the reason inline; add a `Controlled task claimed, connectivity lost` pattern with auto-release; decide the witness-to-commit window explicitly; add the ordering rule witness → commit → move.

## Major

**M1 — A conformance false-accept has no physical remediation path.** Retraction is designed for ledger truth. A conformance rejection on replay means frozen goods are *physically* in an ambient bin and have been for the offline window. The sync summary is a passive post-replay screen; it cannot carry a cold-chain remediation. *Fix:* split ledger retractions from **physical retractions** — the latter generates a high-priority remediation task, quarantines the units, and interrupts rather than waits.

**M2 — FEFO override contradicts itself between the documents.** `DESIGN.md` Colors lists amber for "FEFO-override prompts"; `EXPERIENCE.md` now specifies a flat Rejected refusal with no override path. Different interactions. And an offline override produces a queued op the server may re-refuse. *Fix:* pick one and state it in both. Recommended: shelf-life is an amber override-with-reason for authorized roles (policy); conformance stays a hard red refusal (safety). State whether override works offline, and if so that authorization is re-evaluated on replay with retraction if refused.

**M3 — Container and contents are separate ops with no composite-settlement vocabulary.** FIFO replay can settle the container move while a contents op quarantines, leaving a pallet recorded as moved with items held. The sync summary counts per task and has no composite notion. *Fix:* define container + contents as one replay group, a single expandable row with nested outcomes; if the container settles and any content is held, the container renders queued-quarantine until all resolve.

**M4 — Returns reuse receiving's shape but not its decision basis.** Receiving's offline strength is the PO's expected SKU/quantity set in the task payload — that is what enables a ≤500 ms refusal. A blind return has no cached RA, so every scan becomes Recorded · queued and the server decides later. Honest, but the flow *looks* identical while its offline decision quality is materially weaker, and nothing tells the operator. Second seam: the operator holds the item and makes the judgement, but disposition routes to a web approval card — leaving an unnamed interim state (received, not yet dispositioned): does it hit ATP? *Fix:* state the divergence on the task screen, not just the spec; add a `Received, awaiting disposition` badge excluded from ATP; note in the [NOTE FOR UX] that the component-level reuse claim is unresolved until the disposition owner is named.

**M5 — Queued and Held-for-review share one colour token.** `scan-queued` and `scan-quarantined` are both `{colors.warning}`. "Your work is fine, just waiting" and "the server rejected your work" are the most semantically opposite outcomes for a floor operator, and they differ only by glyph and word. Amber now carries ~7 meanings. *Fix:* keep one amber for status badges, but differentiate the two **banner** states structurally (hatch or bordered fill vs flat) plus a mandatory action affordance on Held that queued never has. This is about 2-metre legibility, the banner's actual job.

**M6 — A scale reading violating declared precision has no defined path.** "Refused inline" presumes a typed value the operator can retype; a scale reporting 18.4567 kg against 0.1 kg precision is a scan-equivalent input the operator cannot edit. And catch-weight *tolerance* is not cached, so an implausible weight queues and is refused server-side after the goods are packed. *Fix:* round hardware readings to declared precision and show both ("Scale: 18.4567 → recorded 18.5 kg"); reserve inline refusal for typed entry; add tolerance to the cached snapshot; state that a captured catch weight survives banner swaps, suspension and backgrounding.

## Minor

**m1** The queue chip shows count but never elapsed offline time — at minute 90 the operator sees the same chip with no signal they are past the guaranteed window while on-device rules age.
**m2** `DESIGN.md`'s Witness capture row omits the online-only constraint, which is the component's single most important behavioural rule.
**m3** The decimal keypad has no focus/preservation rule, unlike the precisely-specified HID capture field; a half-entered quantity has undefined fate on a banner swap.
**m4** Return receipts have no stated idempotency anchor; receiving anchors to the PO line, a blind return has no equivalent.

## Holds up (do not "fix" by accident)

The four-state definition itself; retraction-not-silent-correction; per-badge-in re-authorization on replay; `Device revoked mid-shift` vs `Device revoked (offline)` as separate patterns; `Claim lost` refusing to write off physical picks; offline badge-in restore. The [NOTE FOR UX] refusing to invent the three missing journeys is the right call — C4 and M4 are the component-level consequences of those gaps and should be resolved alongside them, not before.
